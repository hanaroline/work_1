# 사내 AI 활용 가이드라인 준수 — 결정 사항과 미결 과제

2026-09-22 대화에서 사내 「스마트한 AI 활용을 위한 가이드라인」을 이 저장소에
어떻게 적용할지 정했다. 그때 확인한 사실과 아직 끝내지 못한 것을 남긴다.

**규칙 자체는 저장소 루트 `CLAUDE.md` 에 있다.** 이 문서는 "왜 그렇게 정했는가"와
"무엇이 남았는가"를 적은 것이다.

---

## 1. 사내 가이드라인 원문 — 다섯 갈래

| | 리스크 | 가이드라인이 요구하는 것 |
|---|---|---|
| ① | 회사 중요정보·개인정보 노출 | 미공개 정보·내부 문서·고객 개인정보·**소스코드**·정책·전략·실적을 입력/업로드하면 노출 가능 → **마스킹·가명화·익명화**, 내부 문서 요약 전 포함 여부 **반드시 확인** |
| ② | 금융소비자보호법 저촉 | 출처 미표시 정보로 고객 응대 시 **불완전판매** 가능 → 출처를 **명확히 밝히고 반드시 검증·수정·보완** |
| ③ | 저작권 등 지적재산권 침해 | 외부 자료 학습 기반 산출물, 당사 작성물의 AI 입력 → **정보와 자료의 출처를 반드시 검증** |
| ④ | 회사 평판 | 차별·혐오·비윤리적 표현 포함 가능 → **내용 사전 검토 필요** |
| ⑤ | 거짓 답변 | 거짓도 사실처럼 답변 → **업무의 보조수단으로만**, 반드시 사실 확인 |

## 2. 이 프로젝트에서 왜 위험도가 높은가

이 저장소는 **고객 제안서 · ETF 제안 · ELS 상품 검색 · 목표주가 · 증권사 리포트
요약**을 만든다. 즉 ②(금소법) 영역에 정면으로 들어간다. 일반적인 코딩 프로젝트보다
가이드라인 적용을 엄격하게 해야 하는 이유다.

특히 두 가지가 구조적으로 겹친다.

- **타사 리포트 본문을 추출해 공개 웹에 싣는다** → ③ 지적재산권
- **AI가 요약한 내용이 고객 응대에 쓰일 수 있다** → ② 금소법

## 3. "채팅은 안전하다"는 오해 — 두 축을 구분할 것

작업 중 나온 혼동이라 명시해 둔다.

| 축 | 뜻 | 해당하는 것 |
|---|---|---|
| **인터넷 전체 공개** | 누구나 검색·열람 가능 | **GitHub 저장소 `public` 설정**. Chat/Code/Cowork 선택과 **무관** |
| **사외 전송** | 사내 정보가 회사 밖 서버로 나감 | **Chat · Code · Cowork 전부 해당** |

**가이드라인 ①이 문제 삼는 것은 두 번째 축이다.** 채팅창에 회의록을 붙여넣는 것과
Claude Code가 소스코드를 읽는 것은, 가이드라인 관점에서 동일하게 "외부 AI 서비스에
사내 정보를 입력한 행위"다. **채팅이라서 면제되는 것은 없다.**

채팅에도 공개 경로가 있다 — **대화 공유 링크**와 **아티팩트 게시(publish)**.
둘 다 링크를 가진 사람이 열람할 수 있다.

**Cowork 데스크톱은 로컬 파일에 직접 접근**하므로 셋 중 노출 면적이 가장 넓다.
작업 폴더를 그 작업에 필요한 범위로만 지정한다.

### 정정 — 고객제안서 엑셀 (2026-10-01)

2026-09-22 대화에서 `고객제안서_*.xlsx`·`*.xlsm` 을 **"git 미추적"이라고 보고했으나
이는 틀렸다.** 확인 명령이 한글 파일명 인용(quoted path) 때문에 빈 결과를 냈고,
그것을 미추적으로 잘못 읽었다. (`git ls-files` 는 비ASCII 경로를 `"\352\263..."` 로
감싸 출력하므로 `grep '\.xlsx$'` 이 걸리지 않는다. 확인할 때는
`git -c core.quotepath=false ls-files` 를 쓸 것.)

**실제 상태**

| 파일 | 최초 커밋 |
|---|---|
| `고객제안서_월배당ETF.xlsx` | `83db2272` (2026-09-16) |
| `고객제안서_자산배분.xlsx` | `ecd54e26` (2026-09-18) |
| `고객제안서_자산배분_매크로.xlsm` | `d0f005ce` (2026-09-19) |

셋 다 **공개 저장소에 올라가 있다.** 2026-10-01 내용 점검 결과:

- 주민번호·계좌번호·연락처·이메일 패턴 → **실제 해당 없음**
  (정규식에 걸린 13자리 숫자들은 전부 `0.1049382716…` 같은 **비중 소수값**이었다)
- 한글 인명 셀 → 없음. 「연배당」「월배당」「부동산」 등 상품 분류어뿐
- 결론: **시장 데이터로 생성된 템플릿**이며 고객 개인정보는 들어 있지 않다
  (생성: `scripts/build_proposal_xlsx.py`, `build_proposal_xlsm.py`)

**다만 이것은 패턴 스캔이지 전수 감사가 아니다.** 그리고 파일명이 「고객제안서」라
외부에서 실제 고객 자료로 오인할 소지가 있다. → 5-3 참고

## 5. 미결 과제 — 사람의 판단이 필요하다 ★

아래 셋은 Claude가 결정할 수 없다. **새 계정에서 이어받는 사람이 처리해야 한다.**

### 5-1. 저장소 `public` → `private` 전환 검토

가이드라인 ①이 **소스코드를 중요정보로 명시**한다. 현재 저장소는 AI 입력 이전에
이미 인터넷 전체에 공개돼 있다. 회사 업무용 코드·데이터라면 전환을 검토해야 한다.

**다만 GitHub Pages로 대시보드를 배포 중**이라, 전환하면 Pages 접근 방식이 바뀐다.
배포 대상이 누구인지(사내 전용인가, 외부 공유인가)에 따라 결정이 달라진다.
→ 결정 전까지는 `CLAUDE.md` 0절("커밋하는 모든 것은 공개된다고 전제")을 지킨다.

### 5-2. `data/reports/*.json` 리포트 본문 추출 범위 — 저작권 검토

타사 리포트 원문 문장을 추출해 공개 Pages로 배포한다. 가이드라인 ③과 직접 맞닿는다.
내부 참고용 범위 안인지 **컴플라이언스 확인**이 필요하다.
→ 확인 전까지 **추출 범위를 넓히는 변경은 하지 않는다**(문장 수 증가, 전문 저장 등).

### 5-3. 「고객제안서」 엑셀 3종의 공개 저장소 게시 여부

내용에 개인정보는 없으나(4절), **파일명이 「고객제안서」**라 공개 저장소에 올라가
있는 것 자체가 오인·평판 리스크가 될 수 있다. 선택지는 셋이다.

1. 그대로 둔다 — 내용상 템플릿이므로 문제없다고 판단
2. 파일명을 바꾼다 — 예: `제안서템플릿_월배당ETF.xlsx`
3. 산출물이므로 `.gitignore` 로 빼고, 필요할 때 스크립트로 생성한다

→ **3번이 가장 깔끔하다**(생성 스크립트가 이미 있다). 다만 Pages나 다른 문서가
이 파일을 링크하고 있는지 먼저 확인해야 한다.

### 5-4. 이 사용 방식 자체의 사내 승인 범위

Claude Code는 저장소 코드를 외부 모델에 전송한다. 사내 승인된 도구·용도 범위
안인지 확인이 필요하다. 학습 데이터 사용 여부는 계정 유형(개인 Pro/Max vs 회사
Team/Enterprise)에 따라 다르므로 **계정 설정에서 직접 확인**한다.
