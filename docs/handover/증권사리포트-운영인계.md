> 「증권사 리포트 다이제스트」 절에 이미 적혀 있다. 그쪽을 먼저 읽고 이 문서를 본다.

## 0. 새 계정에서 가장 먼저 할 일

1. 새 Claude 계정에 이 저장소(`hanaroline/work_1`)를 연결한다.
2. 이 문서와 `자주쓰는-프롬프트.md`, `시스템설정-백업.md` 를 읽는다.
3. **예약(Routine)을 새로 만든다.** 예약은 계정에 묶여 있어 **계승되지 않는다.**
   만드는 법과 넣을 문장은 `자주쓰는-프롬프트.md` 의 「예약에 넣을 지시문」 그대로.
4. 첫 판을 뽑아 검산 42개가 통과하는지 확인한다.

### 계정이 바뀔 때 넘어오는 것과 안 넘어오는 것

| | 계승 | 비고 |
|---|---|---|
| 저장소의 코드·스크립트·워크플로 | **O** | git 에 있는 것은 전부 |
| `data/reports/*.json` 수집 이력 | **O** | 날짜별 판이 그대로 남는다 |
| `docs/reports/index.html` 화면 | **O** | |
| 이 인계 문서들 | **O** | 그래서 저장소에 넣는다 |
| **대화 기록(이 채팅)** | **X** | 계정에 묶인다 |
| **예약(Routine)** | **X** | 새 계정에서 다시 만들어야 한다 |
| **채팅으로 올렸던 완성 파일** | **X** | 아래 참고 |

**`out/` 는 저장소에 없다.** `.gitignore` 에 들어 있고 컨테이너는 회수된다.
즉 **지금까지 채팅으로 받은 HTML·PDF 파일은 새 계정으로 넘어오지 않는다.**
다만 **자료 자체는 `data/reports/<날짜>.json` 에 남아 있으므로 언제든 다시 뽑을 수 있다**:

```
bash scripts/make_reports_outputs.sh 2026-09-28     # 그날 판을 그대로 재생성
```

받아 둔 파일이 필요하면 **계정을 끝내기 전에 내려받아 두는 편이 안전하다.**

## 1. 이 일이 무엇인가

평일마다 증권사 리포트를 모아 **요약본 한 장 + PDF 셋**으로 만들어 건넨다.

- 요약은 **발췌(extractive)** 다. 본문에 있는 문장을 그대로 옮긴다.
  **새로 쓰지 않고, 셈을 새로 하지 않는다.**
- 원천 여덟 곳: 네이버 리서치 6갈래(종목·산업·시황·투자·경제·채권) +
  미래에셋증권 리서치 + 하나증권 리서치.
- 세션은 사내 이그레스 정책 때문에 원천에 직접 못 붙는다.
  **러너(GitHub Actions)가 대신 받아 저장소에 커밋하고, 세션은 커밋된 JSON 을 읽는다.**

## 2. 날마다 하는 순서 (이대로만 한다)

```bash
cd /home/user/work_1
git fetch origin main && git checkout main && git reset --hard origin/main
BASE=$(git rev-parse origin/main)          # ← 밀어 넣기 **전에** 적어 둔다

bash scripts/request_reports_refresh.sh "11:00 판"

# 러너 커밋을 기다린다. 「리포트 수집 요청」(내가 민 것)과
# 「리포트 수집 2026-…」(러너가 민 것)을 자릿수까지 구별할 것.
until git fetch -q origin main && \
      [ -n "$(git log --format=%h $BASE..origin/main --grep='^리포트 수집 2026')" ]; do
  sleep 30
done

git reset --hard origin/main
python3 scripts/verify_reports.py data/reports/latest.json   # ← 반드시 **먼저**
bash scripts/make_reports_outputs.sh 2026-10-01              # 통과한 뒤에만
```

마지막으로 `out/` 의 네 파일을 사용자에게 올린다.

### 절대 규칙

- **검산이 통과해야만 자료를 낸다.** 나가는 값이 0 이 아니면 내지 않는다.
  42개 「모두 맞음」이라야 통과. 어긋나면 **무엇이 어떻게 어긋났는지 그대로 옮겨 알린다.**
- **숫자는 실린 값과 직접 센 값을 대조해서 적는다.** 요약에 적힌 수를 그대로 믿지 않는다.
- **목표주가 상하향은 본문 근거를 눈으로 확인한 뒤**에만 적는다. 없으면 「없다」고 적는다.
- **어림하거나 지어내지 않는다. 못 한 것은 못 했다고 적는다.**

## 3. 뽑는 시각 — 왜 11:00 인가

실측으로 두 번 옮겼다. 짐작이 아니라 「수집 시각 ↔ 그날 건수」를 세어 보고 정했다.

| 날 | 08:30 | 09:30 | 10:30 | 11:0x | 13:5x | 19:3x | 22:4x |
|---|---|---|---|---|---|---|---|
| 9/21(월) | — | 09:26 **67** | 10:06 95 | — | — | — | 22:47 **143** |
| 9/22(화) | 7 | 30 | 10:18 43 | 11:18 **72** | 13:56 — | — | 22:46 **89** |
| 9/23(수) | 10 | 34 | 09:55 37 · 10:18 43 | 11:24 **64** | — | — | — |
| 9/28(월) | — | — | 10:33 **94** | 11:47 **113** | 13:56 114 | 19:33 **122** | — |
| 9/29(화) | — | — | 10:33 **81** | — | — | — | — |
| 9/30(수) | — | — | 10:52 **89** | 11:23 **91** | — | — | — |
| 10/1(목) | — | — | — | 11:08 **80** · 11:29 **81** | — | — | — |

읽어 낸 것:

- **08시대는 거의 비어 있다**(7~10건). 09:00~09:30 에 크게 늘고, **11시 무렵까지 이어진다.**
- **09:25 판은 하루치의 절반도 못 담는다**(9/21 은 09:26 에 67건인데 최종 143건).
- 10:30 판도 덜 담는다 — 9/28 은 10:33 94건이 11:47 에 113건(**+20%**)이 됐다.
- **오전에 거의 다 들어오는 날이 많다.** 9/22 는 11:52 에 73건이고 22:46 최종이 89건,
  9/28 도 11:47 113건 → 최종 122건. 오후·저녁 증가분은 대체로 한 자릿수~10건대다.
- 다만 **저녁에 리서치 리포트(데일리·주간물)가 더 붙는 날이 있다**(9/28: 9→17건).

그래서 **평일 11:00** 으로 정했다. 「그 시각까지의 판」이지 하루의 완성본은 아니므로,
**보고에 수집 시각을 반드시 적는다.**

### 시각 변경 이력

| 시점 | 예약 | 비고 |
|---|---|---|
| ~9/22 | 09:25 아침 + 22:45 완성본 | 아침 판이 너무 얇았다 |
| 9/23 | 22:45 → **10:30** 으로 이동, 09:25 는 **끔** | 하루 한 번으로 정리 |
| 10/1 | 10:30 → **11:00** | 10:30 도 덜 담는 것이 사흘 내리 확인됨 |

**서버가 예약 시각의 「분」을 만든 시각에 붙잡는다.** 10:30 으로 걸면 10:31,
11:00 으로 걸면 11:06 에 돈다. 정확히 정시에 고정하는 방법은 확인하지 못했다.

## 4. 검산 42개 — 이것이 마지막 방어선

`python3 scripts/verify_reports.py data/reports/latest.json`

여덟 묶음: **가** 수집 정합성 · **나** 셈 재계산 · **다** 인용 무결성 · **라** 오염 ·
**마** 출처 · **바** 주간 · **사** 원천 상태 · **아** 추출 상태.
**사**와 **아**는 「없는 것」을 찾는 검사다 — 원천이 죽었는지, 요약이 안 붙었는지.

통과하면 「모두 맞음」, 어긋나면 **「산출물을 내지 말 것」**을 찍고 나가는 값 1 을 낸다.

### 실제로 걸렸던 것들

| 검사 | 언제 | 무슨 일이었나 | 어떻게 했나 |
|---|---|---|---|
| `사1 모든 원천이 살아 있음` | 9/30 | 미래에셋·하나 **둘이 한꺼번에** 죽음 | **판을 통째로 재호출** → 2분 48초 만에 여덟 곳 정상 |
| `아2 그날 자에 요약이 붙음` | 9/24·9/25 | 「1건 중 0건(0%)」 | **추석 휴장**이라 리포트 자체가 없던 것. 자료를 내지 않음 |

**원천이 죽으면 수집기 안의 재시도로는 안 된다. 판을 통째로 다시 부르면 된다.**
두 번 불러도 안 되면 **자료를 내지 말고 그 사실을 적어 알린다.**

## 5. 겪은 함정 — 같은 실수를 되풀이하지 않기 위해

### 5-1. 「8분 넘으면 멈춘 것」이라고 단정하지 말 것 ★

9/30 에 수집이 18분 걸렸는데 「워크플로가 안 돈다」고 **잘못 보고했다.**
멈춘 것이 아니라 수집 단계가 오래 걸리는 중이었다(원천 둘이 죽어 시간 초과 대기).
9/25 에 「수집이 안 돌았다」고 한 것도 같은 오진이었을 가능성이 크다.

**8분이 지나면 기다리기를 그만두지 말고, 먼저 실행 기록을 열어 본다:**

```
mcp__github__actions_list(method=list_workflow_runs,
                          owner=hanaroline, repo=work_1, resource_id=reports.yml)
→ status 가 in_progress 면 **기다린다.** list_workflow_jobs 로 어느 단계인지 본다.
→ 아예 실행이 없을 때만 진짜 「안 돈 것」이다.
```

다른 파이프라인(매매 타이밍·시세 수집 등)이 도는지도 함께 보면
저장소·계정 문제인지 이 워크플로만의 문제인지 가려진다.

### 5-2. 자정을 넘긴 수집 ★

`fetch_reports.py` 는 **수집한 날짜**로 날짜 파일을 만든다. 00시 이후에 돌면
새 날짜 파일이 시작되어 무더기가 얇아지고, `report_date` 가 **어제**로 잡히기도 한다.
그런 경우에는 `latest.json` 이 아니라 **날짜를 지정해** 뽑는다.

### 5-3. 자료 구조에서 틀리기 쉬운 자리 ★

손으로 대조할 때 실제로 틀렸던 것들이다.

| 틀리기 쉬운 것 | 바른 것 |
|---|---|
| 행의 증권사를 `r['house']` 로 읽음 | **`r['broker']`** |
| 공통 종목을 `multi_house`/`shared_stocks` 로 읽음 | **`summary['crowded_stocks']`** |
| `summary['by_broker'].items()` | **리스트다.** `{x['broker']: x['count'] for x in s['by_broker']}` |
| 행의 `stock` 을 문자열로 봄 | **dict** — `{'code': ..., 'name': ...}` |
| 주간 건수를 `len(weekly['reports'])` 로 셈 | `weekly['reports']` 는 **브리핑용 추린 목록**(18건쯤). 전체 수는 `weekly['count']` |
| 주간 건수를 **주소**로 중복 제거 | `pool_key()` 가 **쿼리 꼬리를 뗀다.** 미래에셋 한 건이 `categoryId` 만 다른 주소 둘로 잡혀 482 대 481 로 어긋났다 — **검산기가 맞고 손 대조가 틀렸다** |

**대조용 한 줄:**

```python
listed = {x['broker']: x['count'] for x in s['by_broker']}
print("증권사 전부 일치:", listed == dict(collections.Counter(r['broker'] for r in td)))
```

### 5-4. `target_from` 은 직전 목표주가가 아니다 ★

값이 `"api"` 인 행이 많은데 **출처 딱지**이지 가격이 아니다.
직전 목표주가는 자료에 수치로 없는 경우가 많다 — **없으면 없다고 적는다.**

### 5-5. 「상향」이라는 낱말에 속지 말 것 ★

9/23 파두 건에서 본문에 **「실적 추정치를 상향 조정했다」**가 있었는데
이것은 **목표주가가 아니라 실적 추정**이다. 근거로 쓰면 틀린다.
진짜 근거는 따로 있었다 — 「목표주가를 11만원으로 상향 조정하며 매수를 추천한다」.

**목표주가 근거는 「목표주가」라는 말이 들어간 문장으로만 댄다.**

### 5-6. 휴장일

`data/calendar/latest.json` 의 `holidays` 에 KRX 휴장일이 들어 있다.
리포트가 1~2건뿐이면 휴장일부터 의심한다. 2026 추석은 9/24(목)·9/25(금)이었고,
그 이틀은 **자료를 내지 않았다**(검산 아2 가 막았고, 그 판단이 맞았다).

### 5-7. 예약 결과를 확인하지 않아 하루를 날린 적이 있다

`send_later` 호출이 「run_once_at must be in the future」로 **거절됐는데 확인하지 않아**
약속한 산출물이 하루 늦었다. **예약을 걸면 돌아온 발사 시각을 반드시 확인한다.**

## 6. 산출물에 관해 정해진 것

### 6-1. 절마다 새 쪽에서 시작 (커밋 `3f125731`)

전체본에서 「오늘자 → 주간 인기 → 전체 목록」이 **각각 쪽 맨 위**에서 열린다.
`docs/reports/index.html` 의 인쇄 CSS:

```css
#weekly-wrap, #listTop { break-before: page; page-break-before: always; }
body.pdf-weekly #weekly-wrap { break-before: auto; page-break-before: auto; }
```

둘째 줄이 중요하다 — 주간본은 `#weekly-wrap` 이 **첫** 덩이라 그냥 두면 **앞에 빈 쪽**이 생긴다.

### 6-2. 애널리스트 실명은 **싣는다** (커밋 `459d4a7d`)

한때 실명을 전부 지웠다가 **되돌렸다.** 지워야 할 이름은 애널리스트가 아니라
**자료를 받는 사람의 이름**이었다. 리포트 작성자 실명은 자료의 일부다.

- 화면·PDF 에 「미래에셋증권 김석환」처럼 증권사 뒤에 붙는다 — 그대로 둔다.
- 받는 이의 이름은 산출물에 **원래부터 없다**(PDF 에 작성자 칸 자체가 없음).
  저장소 전체에서 한 군데 있던 8/6 브리핑 인사말은 지웠다.

### 6-3. 파일 넷

```
out/미래에셋_증권사리포트_YYYYMMDD.html        한 파일 HTML (자료가 안에 박혀 있어 두 번 클릭해 열림)
out/미래에셋_증권사리포트_YYYYMMDD_요약.pdf     그날 판만
out/미래에셋_증권사리포트_YYYYMMDD_주간인기.pdf  주간 절만
out/미래에셋_증권사리포트_YYYYMMDD_전체.pdf     위의 것 + 전체 목록
```

날짜를 지정해 뽑으면 자료가 **두 벌** 박혀 HTML 이 두 배가 된다
(`latest.json` 키와 날짜 키 양쪽에). 담긴 내용은 같다. 가볍게 하려면 `최신` 으로 뽑는다.

## 7. 저장소·브랜치 규칙

- **운영은 `main` 에서 한다.** 예약 수집(schedule)은 기본 브랜치의 워크플로만 발동한다.
- 커밋 메시지 끝에 붙이는 줄:

```
Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>
Claude-Session: https://claude.ai/code/session_…
```

- **모델 이름을 저장소에 밀어 넣지 않는다** — 커밋 메시지·PR·코드 주석 어디에도.
  (위 `Co-Authored-By` 는 계정이 지정한 형식이라 예외.)
- **요청하지 않은 PR 을 만들지 않는다.**
- `out/`·`out-test/` 는 `.gitignore` 에 있다. 산출물은 저장소에 남기지 않는다.
