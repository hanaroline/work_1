# 국내 100대 기업 대시보드 — 운영 인계

**작성 2026-10-01 · 대상 파일 `kr-top100.html` (저장소 `hanaroline/work_1`)**

지금 쓰던 Claude 유료 계정을 닫고 새 계정에서 이어 갈 때 읽는 문서입니다.
저장소의 다른 작업은 `docs/HANDOVER.md`(브리핑)와 `docs/handover/` 의 다른 문서가
맡습니다. **이 문서는 국내 100대 기업 화면 한 가지만** 다룹니다.

짝이 되는 문서: `docs/handover/미국100대기업-대시보드-인계.md`.
두 화면은 **수집기를 함께 씁니다**(4절). 미국 쪽을 고칠 때 국내가 함께 흔들릴 수
있으니 그 문서도 같이 보십시오.

## 1. 계정을 바꾸면 무엇이 넘어가는가

**저장소에 든 것은 전부 넘어가고, 계정에 묶인 것은 넘어가지 않습니다.**

### 넘어가는 것 — GitHub 저장소에 있습니다

| 무엇 | 어디 |
|---|---|
| **화면 파일 자체** | `kr-top100.html` — 100종목 목록·검색 키워드·한글 개요·화면 코드가 전부 이 한 파일에 |
| **수집된 시세·지표·차트·오프라인 판** | 브랜치 `kr100-data` 의 `data/kr100/` |
| **수집 자동화** | `.github/workflows/kr100-data.yml` · `kr100-quotes.yml` · `kr100-ranking.yml` · `kr100-offline.yml` · **`kr100-weekly.yml`** |
| **수집기·도구** | `scripts/fetch_kr100.py` · `fetch_kr100_quotes.py` · `check_kr100_ranking.py` · **`update_kr100_list.py`** · `make_offline_html.py` · `publish_kr100_data.sh` |
| **커밋 이력 전체** | 무엇을 왜 고쳤는지가 커밋 메시지에 남아 있습니다 |
| **이 문서** | `docs/handover/국내100대기업-대시보드-인계.md` |

> GitHub Actions 는 **계정이 아니라 저장소**에 붙어 있습니다. Claude 계정을 닫아도
> 시세 수집·가격 갱신·주간 목록 교체는 그대로 돕니다. 이미 배포한 오프라인 파일을
> 쓰는 동료의 화면도 영향받지 않습니다.

### 넘어가지 않는 것 — 옛 계정에 묶여 있습니다

| 무엇 | 어떻게 할 것인가 |
|---|---|
| **대화 기록 전체** | 되살릴 수 없습니다. 이 문서가 그 자리를 대신합니다 |
| **예약(Routine)·세션 체크인** | 이 화면은 **예약이 필요 없습니다** — 주간 갱신이 GitHub Actions 안에 있습니다(6절). 다른 갈래의 예약은 `docs/handover/자주쓰는-프롬프트.md` 2절 참고 |
| 발행한 아티팩트·채팅에 올린 파일 | 파일 본체는 저장소에 있으니 다시 내려받으면 됩니다 |

**이 화면이 다른 갈래보다 이관에 강한 이유**가 여기 있습니다. 미국 화면의 주간 교체는

계정을 닫아도 매주 목록이 시가총액 순위를 따라갑니다.

## 3. 두 가지 판 — 실시간 판과 오프라인 판

| | **실시간 판** | **오프라인 판** |
|---|---|---|
| 파일 | `kr-top100.html` (약 380KB) | `kr-top100-offline.html` (약 4.3MB) |
| 어디서 | 저장소 루트 | 데이터 브랜치의 고정 주소 ↓ |
| 데이터 | 열 때 브라우저가 받아옵니다 | **HTML 안에 박혀 있습니다** |
| 쓸 자리 | 인터넷 되는 PC | **인터넷이 막힌 업무용 PC** |

```
https://raw.githubusercontent.com/hanaroline/work_1/kr100-data/data/kr100/kr-top100-offline.html
```

열어서 **다른 이름으로 저장** 하면 됩니다. 늘 가장 새 판입니다.

> **오프라인 판이 따로 필요한 까닭**: `file://` 로 열린 페이지는 **옆에 있는 json
> 파일조차** CORS 로 못 읽습니다(origin `null`). 데이터를 같이 복사해 두어도 소용이
> 없어서, HTML 안에 넣는 수밖에 없습니다.

두 판은 **같은 화면**입니다. 오프라인 판에서 내장 데이터 블록(`<script
id="kr100-embedded">`)만 떼어 내면 `kr-top100.html` 과 바이트까지 같습니다.
오프라인 판은 배지에 `내장 스냅샷 10.01 19:56` 처럼 **만든 시점을 밝히므로** 오래된
파일을 실시간 시세로 착각할 일은 없습니다.

## 4. 구조 — 데이터가 흐르는 길

```
GitHub 러너가 야후에서 받아
  → data/kr100/ 에 쓰고
  → 부모 없는 커밋 하나로 브랜치 kr100-data 를 갈아 끼우고
  → 화면이 raw.githubusercontent 에서 읽는다
```

`main` 히스토리에 쌓지 않습니다 — 차트 100개(약 3MB)와 오프라인 판(약 4.3MB)이 날마다
통째로 바뀌므로 쌓으면 저장소가 1년에 여러 GB 로 붇습니다. 지금 조회되는 값만 의미가
있어 **과거를 보관하지 않습니다**. 실제 일은 `scripts/publish_data_branch.sh` 가 합니다.

### 수집기는 미국 화면과 **같은 엔진**입니다

`scripts/fetch_us100.py` 가 엔진이고, `fetch_kr100.py` 는 시장 프로필만 갈아 끼워
부르는 얇은 진입점입니다.

```python
engine.configure(market="kr", page=.../kr-top100.html, out_dir=.../data/kr100,
                 currency="KRW", stooq_suffix=".kr", exchanges=("KSC","KOE","KDQ"), note=...)
engine.main()
```

**그래서 `fetch_us100.py` 를 고치면 국내 수집도 함께 바뀝니다.** 미국 쪽을 손본 뒤에는
국내 수집도 한 번 돌려 보십시오. 코드를 두 벌 두지 않으려고 이렇게 했고, 지금까지
회귀가 난 적은 없지만 그건 매번 둘 다 돌려 봤기 때문입니다.

### 수집 일정 (한국시간)

| 워크플로 | 언제 | 하는 일 |
|---|---|---|
| `kr100-quotes.yml` | 정규장 09:00~15:50 10분 주기 + 장전·장후 30분 | 가격만 → `quotes.json` |
| `kr100-data.yml` | 평일 15:45 (마감 뒤) | 전 종목 시세·지표·실적·뉴스 → `latest.json` + `chart/` + **오프라인 판** |
| `kr100-ranking.yml` | 평일 16:10 | 시총 상위 100 과 목록 비교 → `ranking.json` + 이슈 갱신 |
| `kr100-offline.yml` | `kr-top100.html` 을 고쳐 push 할 때 | 수집 없이 **오프라인 판만** 30~60초에 다시 만들어 올림 |
| **`kr100-weekly.yml`** | **월요일 10:00~17:00 매시 + 다른 워크플로가 끝날 때마다** | **목록 교체**(6절) |

손으로 돌릴 때:

```bash
python scripts/fetch_kr100.py                      # 전체 수집
python scripts/check_kr100_ranking.py              # 목록 점검
python scripts/update_kr100_list.py                # 목록 교체
python scripts/make_offline_html.py --market kr --out kr-top100-offline.html
```

## 5. 유지해야 할 작업 규칙

### 디자인
미래에셋 디자인 체계를 따릅니다 — 오렌지 `#F58220`, 블루 `#043B72`, 표 머리글 `FAB072`.
한/영 토글은 `data-ko`/`data-en` 속성으로 합니다. 외부 라이브러리를 들이지 않습니다
(폰트 CDN 하나만 예외). 화면 하나가 **파일 하나**인 것이 이 저장소의 약속입니다.

### 국내 시장에 맞춘 표기
- 큰 금액은 **조·억원** (`421조원` · `4,300억원`), 주당 금액은 **원 단위, 소수점 없이**
- 종목코드 6자리 + `.KS`(코스피) / `.KQ`(코스닥)
- 장 시간은 `Asia/Seoul` — 장전 08:30 · 개장 09:00 · 마감 15:30 · 장후 18:00
- 뉴스는 **한글이 먼저**입니다(구글 뉴스 RSS `hl=ko`). 영문 뉴스는 보조입니다

### 정직성 — 이 화면에서 가장 중요한 규칙
- **없는 값은 「미조회」로 둡니다.** 지어내지 않습니다.
- 자동으로 지은 개요는 **자동이라고 밝힙니다**(6절의 `'auto'` 표시).
- 커버리지를 적을 때는 **실측치**를 적습니다. 처음에 "국내는 목표주가가 대부분 없다"고
  적었다가 실제로 재 보니 99/100 이었습니다. 화면·README·주석 네 곳을 고쳤습니다.
  (2026-10-01 실측: 시세·시총·PER·PBR·실적 100 · 한글뉴스 100 · 목표주가 99 ·
  투자의견 98 · 컨센서스 EPS 75 · 확정 실적발표일 66)

### 코드
- 파이썬은 **표준 라이브러리만**. 깔 것이 없어야 합니다.
- 화면을 고쳤으면 **크로미움으로 열어 보고** 보고합니다. "고쳤다"로 끝내지 않습니다.
- 워크플로는 `python3 -c "import yaml; yaml.safe_load(...)"` 로 파싱을 확인합니다.

## 6. 100종목 목록은 **매주 저절로 바뀝니다**

이 화면이 미국 화면과 가장 크게 다른 점입니다.

### 규칙

| | 값 | 왜 |
|---|---|---|
| 들어오는 조건 | 시총 **90위 안** | |
| 나가는 조건 | 시총 **110위 밖** | 사이 완충 구간이 100위 언저리에서 매주 오가는 종목을 걸러 줍니다 |
| 한 번에 | 최대 **5종목** | 순위 원천이 하루 이상해도 목록이 통째로 흔들리지 않게 |
| 목록 크기 | 항상 100 | 들어오는 수와 나가는 수를 맞춥니다 |

조정하려면 `scripts/update_kr100_list.py` 머리의 `ADD_RANK`·`DROP_RANK`·`MAX_SWAP`
또는 수동 실행 입력(`add_rank`·`drop_rank`·`max_swap`)을 씁니다.

> **완충 구간이 넓으면 목록이 천천히 뒤처집니다.** 2026-10-01 현재 90위 안에 들어온
> 후보가 둘(대덕전자 82위 · 원익IPS 86위) 있는데도 교체가 일어나지 않습니다 — 우리 목록의
> 꼴찌가 **정확히 110위**라 «110위 밖» 조건에 걸리지 않기 때문입니다. 설계대로 도는
> 것이고(흔들림보다 안정을 택한 값), 더 촘촘히 따라가게 하려면 `DROP_RANK` 를 105
> 안팎으로 낮추면 됩니다. **사람이 정할 값이라 임의로 바꾸지 않았습니다.**

### 새 종목의 한글 자산을 **도구가 지어 넣습니다**

예전에는 이것이 사람 손이어서 자동 교체를 못 했습니다 — 검색 키워드와 "기업 한눈에"
개요가 없으면 그 종목만 화면이 반쯤 빕니다.

| 무엇 | 어디서 |
|---|---|
| 한글 사명 | 상장공시시스템(KIND) → 없으면 **야후에 한국어(`lang=ko-KR`)로 질의** → 그래도 없으면 영문명 |
| 업종 코드 | 사명(지주·은행·제약 등) → 야후 `industry` → 야후 `sector` 순 |
| 검색 키워드 | 업종 기본어 + **영문 개요에서 뽑은 한글 검색어**(`DESC_KO` 대응표) |
| 기업 개요 | 수집한 사실만 — 상장 시장·업종·최근 12개월 매출·영업이익률·시총 순위·임직원 수 |

**셋 중 하나라도 못 만들면 그 종목은 넣지 않습니다.** 다음 주에 다시 봅니다.
목록을 고친 뒤 재수집에서 새 종목의 시세가 안 오면 커밋하지 않고 **되돌립니다.**

자동으로 지은 개요는 `PROFILE_KO` 항목의 **네 번째 자리에 `'auto'`** 가 붙고, 화면의
출처 문구가 "사람이 쓴 요약이 아니다"라고 밝힙니다. 사람이 문장을 고치면 그 `'auto'`
표시만 지우면 됩니다.

### 안전장치
- 고치기 **전과 후** 모두 정합성을 검사합니다 — 목록 100개, 키워드·개요가 목록과 정확히
  짝, 기본 비교 조합이 목록에 없는 종목을 가리키지 않음. 어긋나면 **파일을 쓰지 않습니다.**
- 빠지는 종목이 기본 비교 조합에 있으면 **같은 업종의 다른 종목으로 자동 교체**합니다.
  (예전에 리노공업·엔씨소프트가 조합에 남아 데이터 없는 «유령 칩»이 떴습니다.)
- 손대지 않는 항목의 원문은 **한 글자도 바뀌지 않습니다** — 사람이 쓴 문장이 다시 찍히며
  따옴표·줄바꿈이 달라지는 일이 없게 원문을 그대로 옮깁니다.

### 미리 보기
```bash
python scripts/update_kr100_list.py --probe 052690,039030   # 들어오면 뭐가 적힐지만
python scripts/update_kr100_list.py --dry-run               # 뭘 바꿀지만, 파일은 그대로
python scripts/update_kr100_list.py --check                 # 지금 파일의 앞뒤만 확인
```

## 7. 깃허브 예약은 믿을 것이 못 됩니다 — 그래서 이렇게 짰습니다

**이 저장소에서 실제로 잰 것입니다(2026-09-14).** 하루 동안 도착한 예약 이벤트가
**시간당 한 건 안팎**이었습니다.

```
00:04 market-data · 00:43 els · 01:20 kr100-quotes
01:36 reports    · 02:41 kr100-quotes · 05:05 reports
```

`kr100-quotes` 는 `*/10 0-6 * * 1-5` — 아침에만 42번 발동해야 하는데 한 번 왔습니다.
주간 갱신의 01:00 슬롯은 **오지 않았고**, 여덟 슬롯으로 늘린 뒤에도 03·04·05 UTC 가
모두 빠졌습니다. 다른 워크플로는 받고 있었으니 설정 문제가 아니라, 깃허브가 이
저장소의 예약을 드문드문 흘려 보내고 그 적은 배달을 열 개 남짓한 워크플로가 나눠
갖는 상황입니다.

**주 1회 한 슬롯짜리 일정은 이런 곳에서 가장 먼저 굶습니다.** 그 한 번을 놓치면 한 주가
통째로 비고 재시도도 없습니다. 그래서 저절로 불리는 길을 **둘**로 두었습니다.

| 길 | 언제 |
|---|---|
| 예약 | 월요일 10~17시 KST, 한 시간 간격 여덟 번 (`0 1-8 * * 1`) |
| `workflow_run` | `국내 100대 기업 가격 갱신`·`시세 수집` 이 끝날 때마다 |

그리고 **먼저 도착한 하나만 일합니다.** 첫 단계가 «이번 주에 이미 일한 판이 있는지»를
보고 있으면 건너뜁니다(체크아웃도 하지 않는 10초짜리 빈 판). 한 주에 수십 번 불려도
일하는 것은 하나입니다.

### ★ 가드는 **산출물**을 묻습니다 — 실행 기록이 아니라

처음에는 실행 기록(Actions runs)을 셌는데 **그것이 스스로를 막습니다.** 가드에 걸려 몇 초
만에 끝난 «빈 판»도 결론은 `success`, event 는 `workflow_run` 이라, 다음 판이 그것을
"이번 주에 돌았다"로 읽습니다. 상류인 가격 갱신이 월요일 00:00 UTC(09:00 KST)부터
끝나므로 **10시 문이 열리기도 전에 빈 판이 쌓이고, 문이 열리자마자 스스로 막힙니다.**

같은 가드를 가져다 쓴 캘린더 쪽에서 2026-09-28 에 실제로 그렇게 **한 주가 통째로
비었습니다**(`HANDOFF.md` 5절 «함정 2»). 국내 쪽은 상류가 늦게 끝나 아직 터지지 않았을
뿐이어서, 2026-10-01 에 같은 방식으로 고쳤습니다.

지금은 **`data/kr100/list-change.json` 의 `builtAt`** 이 이번 주 월요일 01:00 UTC 이후인지를
봅니다. 이 파일은 **일한 판만** 데이터 브랜치에 올립니다 — 바뀐 것이 없는 주에도 올리고,
빈 판은 체크아웃조차 하지 않으므로 올릴 수 없습니다. 속일 수 없는 잣대입니다.

미리보기(`probe`)·가늠(`dry-run`)은 목록을 건드리지 않았으므로 기록도 남기지 않습니다.
앞 단계가 실패하면 기록 단계까지 오지 않으므로 **실패한 주는 «끝난 주»가 되지 않고**
다음 기회에 다시 돕니다.

월요일 슬롯이 전부 빠진 주에는 **그 주의 다음 기회가 대신 일합니다** — 목표는 월요일
10시지만, 한 주를 통째로 거르는 것보다 늦게라도 도는 편이 낫기 때문입니다.
사람이 부른 수동 실행·push 는 이 가름을 거치지 않고 언제나 돕니다.

## 8. 겪은 함정 (같은 실수를 되풀이하지 않도록)

1. **CSS 를 넣었는데 아무 일도 안 일어난다** — 좁은 화면 규칙을 기존
   `@media (max-width:1080px)` 블록 **앞**에 두면 뒤따르는 `#list-table tbody td`
   규칙(우선순위가 높음)에 덮입니다. 반드시 **뒤에** 두십시오. 표 넘침이 정확히 38px 에서
   꿈쩍 않던 것이 이것이었습니다.

2. **표가 잘린다** — 열이 13개인데 원화 금액이 달러보다 깁니다(`1,853,000원` vs
   `$173.45`). 금액 단위를 칸에서 빼 **열 머리글로** 옮기고(`현재가 (원)` ·
   `시가총액 (조원)`), 업종은 **표에서만 짧은 이름**을 씁니다(전체 이름은 `title` 로).
   지금 1024~1600px 에서 한·영 모두 넘침 0px 입니다.

3. **한글 머리글이 단어 중간에서 갈린다**(`상승여`/`력`) — `word-break:keep-all` 과
   단위 앞 공백으로 그 자리에서만 접히게 합니다.

4. **오프라인 판에 가격이 안 담긴다** — 오프라인 판을 만들기 전에 데이터 브랜치에서
   `quotes.json`·`ranking.json` 을 받아 와야 합니다. 그러지 않으면 코드 브랜치의 안내
   파일(`{"movedTo": …}`)이 그대로 담겨 `가격 0종목` 으로 나갑니다. **실제로 그렇게
   한 번 나갔습니다.**

5. **전체 수집이 통째로 취소된다** — 잡의 `timeout-minutes` 를 넘기면 Actions 가
   `cancelled` 로 적어 **실패처럼 보이지 않습니다.** 야후가 느린 날 종목당 30초(평소
   3.5초)가 걸려 59/100 에서 잘렸고, 이틀치 수집이 조용히 없었습니다. 지금 전체 수집
   75분 · 주간 갱신 90분으로 두었습니다.

6. **한국거래소는 러너에서 막힙니다** — `data.krx.co.kr` 의 `getJsonData` 는 HTTP 400 +
   본문 `LOGOUT`, 상장공시시스템 `kind.krx.co.kr/corpgeneral/corpList.do` 는 HTTP 403.
   클라우드 IP 차단이라 헤더로 풀리지 않습니다. 그래서 순위는 **야후 스크리너
   (`region=kr`)**, 한글 사명은 **야후 `lang=ko-KR`** 에서 받습니다. 사내망처럼 국내 IP
   가 나가는 자리에서 손으로 돌리면 KIND 가 열려 더 나은 이름·키워드가 들어갑니다.

7. **우선주가 순위를 망칩니다** — 야후가 삼성전자 우선주(005935)에 보통주 기준 시총을
   붙여 3위로 올려 보냅니다. 종목코드 끝자리가 `0` 이 아닌 것을 걸러냅니다. 스팩·리츠도
   «기업이 아닌 것»이라 모집단에서 뺍니다.

8. **코드만으로 시장을 고르면 틀립니다** — 039030(코스닥)에 `.KS` 를 붙여도 야후가 빈
   차트를 돌려주어 그대로 굳었습니다. 야후 검색이 돌려주는 심볼을 씁니다.

9. **README 가 62MB 로 터진 적이 있습니다** — `s.index(...)` 가 더 앞의 자리를 찾아
   빈 문자열이 되었고 `s.replace("", 새글)` 이 **글자 사이마다** 새 글을 끼워 넣었습니다.
   치환 전후로 `count == 1` 을 확인하십시오.

## 10. 질문: 새 계정에 연동하면 과거 작업이 계승되는가

**파일·데이터·자동화·이력은 전부 계승되고, 대화는 계승되지 않습니다.**

GitHub 저장소는 Claude 계정과 별개입니다. 새 계정에서 `hanaroline/work_1` 을 연동하면
화면 파일, 100종목 목록, 한글 개요, 수집된 시세, 워크플로, 커밋 메시지가 그대로
있습니다. Actions 는 그 사이에도 계속 돌고 있었을 것입니다.

**없는 것은 대화 기록입니다.** "왜 이렇게 했는지"는 커밋 메시지와 이 문서에만 남습니다.
그래서 이 저장소는 결정의 이유를 커밋 메시지에 길게 적는 쪽을 택했습니다.
새 대화는 그것을 읽고 이어 가면 됩니다.
