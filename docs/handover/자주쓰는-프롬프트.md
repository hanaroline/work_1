# 자주 쓰는 프롬프트 · 예약 지시문 모음

마지막 갱신 2026-10-01 · 새 Claude 계정에서 그대로 복사해 쓰기 위한 보관본.

## 1. 날마다 쓰는 짧은 말

실제로 주고받으며 굳어진 표현들이다. 길게 쓸 필요 없다.

| 하고 싶은 것 | 이렇게 말한다 |
|---|---|
| 지금 기준으로 자료 만들기 | `지금 기준으로 자료 뽑아줘` |
| 한 번 더 (최신 반영) | `지금 다시 뽑아줘` / `지금 한 번 더 뽑아줘` |
| 건수만 궁금할 때 | `지금은 리포트 몇 건 정도야?` |
| 예약 시각 확인 | `오늘 증권사 리포트 자동 생성 예약 시간이 몇 시로 설정돼 있어?` |
| 예약 시각 바꾸기 | `평일 11시에 자동예약되도록 걸어둬` |
| 예약 끄기 | `09:25 예약은 꺼줘` |
| 나중에 하기 | `오늘자도 이따 작업해줘. 11시 정도에 하면 좋겠어.` |
| 예약 시각에 맞춰 하기 | `오늘 예약 시간에 작업해줘` |
| 유입 흐름 묻기 | `가장 많이 들어오는 시간은 대략 언제쯤일까?` |
| 마무리 | `오늘은 이걸로 마무리할게` |

### 날짜를 알려 줄 때

세션의 시계가 UTC 기준이라 **한국 날짜와 하루 어긋나 보일 때가 있다.**
헷갈릴 일을 없애려면 이렇게 시작한다:

```
오늘은 2026년 10월 1일이야.
오늘자 최신 증권사 리포트 자동요약해줘.
```

> 받는 쪽은 `TZ=Asia/Seoul date` 로 **반드시 다시 확인**한다. 하네스가 알려 주는
> 날짜는 UTC 기준이라 저녁·밤에는 한국 날짜가 하루 앞선다.

## 2. 예약(Routine)에 넣을 지시문 — **전문 그대로**

새 계정에서는 예약을 다시 만들어야 한다. 아래를 **그대로** 붙여 넣는다.

- 예약 이름: `증권사 리포트 자동 배포 (평일 11:00 KST · 이 대화로 전달)`
- cron: `0 2 * * 1-5`  (UTC 02:00 = 한국 11:00, 평일만)
- 전달 방식: **쓰고 있는 대화로 전달**(persistent session).
  새 대화를 띄우는 방식은 쓰지 않는다 — 그쪽은 저장소에 밀어 넣을 자격이 없어
  아무것도 만들어 내지 못했다.

```text
오늘 자 증권사 리포트를 뽑을 시각입니다(평일 11:00 KST). 늘 하던 순서 그대로, main 에서 합니다.

왜 11:00 인가 — 10:30 판이 하루치를 덜 담는 것을 사흘 내리 실측했습니다.
9/28 은 10:33 에 94 건이던 것이 11:47 에 113 건(+20%), 9/30 도 10:52 89 건 →
11:23 91 건으로 그 시각까지 계속 들어오고 있었습니다. 08 시대는 거의 비어
있고(7~10 건), 09:00~09:30 에 크게 늘었다가 11 시 무렵까지 이어집니다.
다만 하루가 끝난 값은 아니므로, 이 판은 「그 시각까지의 판」이지 완성본이
아닙니다 — 보고에 수집 시각을 반드시 적습니다.

1. git fetch origin main && git checkout main && git reset --hard origin/main

2. 수집을 직접 부릅니다 — 예약(GitHub cron)을 기다리지 않습니다.
   BASE=$(git rev-parse origin/main)   # 밀어 넣기 전에 적어 둔다
   bash scripts/request_reports_refresh.sh "11:00 판"

3. 러너가 끝나기를 기다립니다. 「리포트 수집 요청」(내가 민 것)과
   「리포트 수집 2026-…」(러너가 민 것)을 헷갈리지 않게 자릿수까지 봅니다.
     until git fetch -q origin main && [ -n "$(git log --format=%h $BASE..origin/main --grep='^리포트 수집 [0-9]')" ]; do sleep 30; done
   보통 2 분 30 초~3 분 30 초입니다.

   **8 분이 지나도 안 오면 기다리기를 그만두지 말고, 먼저 실행 기록을
   열어 보십시오.** 9/30 에 18 분이 걸린 적이 있는데, 그때 「안 돈다」고
   보고한 것은 틀린 판단이었습니다 — 멈춘 것이 아니라 수집 단계가 오래
   걸리는 중이었습니다. 멈춘 것인지 느린 것인지는 기록을 봐야 압니다.
     mcp__github__actions_list(method=list_workflow_runs, owner=hanaroline,
       repo=work_1, resource_id=reports.yml)
     → status 가 in_progress 면 기다린다. list_workflow_jobs 로 어느 단계인지 본다.
     → 아예 실행이 없으면 그때가 진짜 「안 돈 것」이다.
   끝내 못 받으면 저장소에 있는 가장 최근 판으로 진행하되 「11:00 수집이
   돌지 않아 ○시 ○분 판을 썼다」고 반드시 적어 알립니다.

4. git reset --hard origin/main 뒤 검산을 **먼저** 돌립니다.
   python3 scripts/verify_reports.py data/reports/latest.json
   나가는 값이 0 이 아니면 자료를 내지 않습니다. 어느 검사가 어떻게 어긋났는지
   그대로 옮겨 알리고, 원인을 찾아 고친 뒤 다시 돌립니다. 42 개 「모두 맞음」이
   나와야 통과입니다.

   **사1 에 원천이 죽었다고 나오면** 곧바로 판을 통째로 한 번 더 부르십시오.
   9/30 에 미래에셋·하나 둘이 한꺼번에 죽었는데(18 분 지연의 원인), 다시
   부르니 2 분 48 초 만에 여덟 곳 모두 정상으로 들어왔습니다. 수집기 안의
   재시도로는 안 되고 판을 통째로 다시 부르면 되는 양상입니다. 두 번 불러도
   안 되면 자료를 내지 말고 그 사실을 적어 알립니다.

5. 통과했으면 그날 날짜를 주어 뽑고 SendUserFile 로 네 파일을 올립니다.
   bash scripts/make_reports_outputs.sh <오늘 날짜 YYYY-MM-DD>

6. 보고에 담을 것 — 숫자는 실린 값과 reports 배열을 직접 센 값을 대조해 적습니다.
   - 오늘 자 몇 건 · 전체 몇 건 · 한 주 몇 건 · 증권사 몇 곳 · 죽은 원천
   - 머리 요약(overview 의 text) 원문 그대로
   - 목표주가를 올리거나 내린 리포트 — 있으면 **본문 근거를 눈으로 확인한 뒤**
     그 문장을 옮겨 적고, 없으면 없다고. 「실적 추정치를 상향」 같은 문장은
     목표주가 근거가 아니므로 쓰지 않습니다.
   - 검산 42 개 통과 여부 · 수집 시각 · 앞날 같은 시각 판과의 비교

어림하거나 지어내지 않습니다. 못 한 것은 못 했다고 적습니다.
```

## 3. 새 대화를 시작할 때 던지는 첫 말

계정을 옮긴 뒤 첫 대화에서 맥락을 심는 용도.

```text
이 저장소에서 평일마다 증권사 리포트 다이제스트를 만들어 왔어.
docs/handover/증권사리포트-운영인계.md 와 docs/handover/자주쓰는-프롬프트.md 를
먼저 읽고, 거기 적힌 규칙대로 작업해줘.

특히 이 셋은 꼭 지켜줘:
1. 검산 42개가 「모두 맞음」이라야 자료를 낸다. 어긋나면 내지 말고 그대로 알려줘.
2. 숫자는 실린 값과 직접 센 값을 대조해서 알려줘.
3. 목표주가 상하향은 본문 근거를 눈으로 확인한 뒤에만 적어줘. 없으면 없다고.

오늘은 2026년 ○월 ○일이야. 오늘 자 자료를 만들어줘.
```

## 4. 거드는 말 — 상황별

### 자료를 내지 말아야 할 때 (검산 실패)

> 어느 검사가 어떻게 어긋났는지 그대로 알려줘. 자료는 내지 마.

### 원천이 죽었을 때

> 판을 통째로 한 번 더 불러줘. 두 번 불러도 안 되면 자료 내지 말고 알려줘.

### 수집이 늦을 때

> 멈춘 건지 느린 건지 실행 기록부터 확인해줘.

### 과거 날짜를 다시 뽑고 싶을 때

> 2026-09-28 자 판을 다시 뽑아줘.
> (→ `bash scripts/make_reports_outputs.sh 2026-09-28`)

### 쪽 나눔·표기를 손볼 때

> 기존 판은 그대로 두고 out-test 에 새로 뽑아서 비교해줘.

## 5. 이 사람과 일할 때의 결

지금까지 오가며 굳어진 것들. 새 계정에서도 같게 유지하면 좋다.

- **한국어로, 문어체로.** 짧고 단정한 문장. 군더더기 인사 없이 본론부터.
- **숫자는 표로.** 시각별 건수 변화는 표가 제일 잘 읽힌다.
- **틀렸으면 틀렸다고 적는다.** 「앞서 ○○라고 한 것은 틀렸습니다」처럼
  고쳐 적되, 길게 자책하지 않고 바로 다음으로 넘어간다.
- **추정과 사실을 구분해 적는다.** 「…로 보이지만 확인한 것은 아닙니다」.
- **먼저 묻기보다 먼저 재어 본다.** 「11시에 뽑으면 더 늘어날까?」 같은 물음에는
  짐작으로 답하지 말고 **실제로 수집을 한 번 돌려 숫자로** 답했다.
- 작업이 끝나면 **다음에 무엇이 있는지** 한 줄로 알려 준다
  (「다음은 내일(금) 11:06 자동 배포입니다」).

## 6. 고객 자산배분 제안서 도구

시황 브리핑·증권사 리포트와 **다른 일거리**다. 예약으로 돌지 않고
**필요할 때 부른다.** 자세한 맥락은 `제안서도구-운영인계.md` 에 있다.

### 6-1. 날마다 쓰는 짧은 말

| 하고 싶은 것 | 이렇게 말한다 |
|---|---|
| 최신치로 다시 짓기 | `제안서 최신치로 업데이트해줘` |
| 완성본 받기 | `완성된 최종본 파일 올려줘` |
| 선정 결과만 보기 | `최종선정 보여줘` |
| 시세를 더 받아오기 | `해외주식도 KIS에서 다년 일봉 받아와` |
| 환율까지 반영 | `환율도 받아서 원화 환산으로 다시 재줘` |
| 수집 상태 묻기 | `수집 끝났어?` / `끝나면 결과 알려줘` |
| 매크로가 도는지 | `엑셀 매크로 실제 동작하는지 확인할 방법 없어?` |

### 6-2. 다시 지을 때 — **아무것도 안 받고 2 분**

받아 둔 시세·기준가·환율이 저장소에 있다. 수집은 보통 필요 없다.

```text
제안서 도구를 최신치로 다시 지어줘. 수집은 하지 말고,
data/proposal/ 에 받아 둔 자료로 universe → html → xlsx → xlsm 차례로.
다 짓고 나면 매크로가 실제로 도는지 verify_xlsm_macro.py 로 확인하고,
자산군별 최종선정 다섯씩 보여준 다음 완성본 파일을 올려줘.
```

### 6-3. 자료를 새로 받아야 할 때

**세션에서는 KIS·네이버·환율 원천에 닿지 않는다.** 러너(GitHub Actions)로
돌려야 한다. 워크플로가 **기본 가지에 있어야** `workflow_dispatch` 가 뜬다.

```text
KIS에서 해외 일봉을 10해치 다시 받아줘. 모의투자(vps)로, 초당 한 번씩.
워크플로를 main 에 먼저 올리고 돌린 다음, 끝나면 결과 알려줘.
```

### 6-4. 이 도구에서 **반드시 지켜 달라고 해야 하는 것**

새 대화에서 처음 시킬 때 이 네 줄을 함께 준다. 전부 **실제로 사고가 났던
것**이고, 말해 두지 않으면 같은 자리에서 되풀이된다.

```text
작업 규칙 넷:
1) 상품은 크기순이 아니라 위험 대비(다년)로 고른다. 목록 앞에서 자르지 말 것.
2) 못 잰 숫자는 비우고 왜 못 쟀는지 적는다. 지어내지 않는다.
3) 기계로 확인 못 하는 것은 넣지 않는다. 넣었으면 눌러서 확인한 결과를 보여 달라.
4) 검사 단계에 `|| true` 를 쓰지 않는다. 실패는 실패로 끝나야 한다.
```

### 6-5. 열쇠를 다룰 때 — **채팅에 붙여 넣지 않는다**

- KIS APP Key / Secret 은 **GitHub Secrets** 에만 둔다. 대화창에 쓰지 않는다.
- **Secret 의 「이름」은 암호화되지 않는다.** 이름 자리에 열쇠를 넣은 적이
  한 번 있었다. 이름은 `KIS_APP_KEY` 처럼 **무엇인지만** 적는다.
- 열쇠·토큰을 커밋하지 않는다. TLS 검증을 끄거나 `HTTPS_PROXY` 를 풀지 않는다.
