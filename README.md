# 종목 통합 리포트 대시보드

주식 종목명 또는 종목코드를 입력하면 해당 종목의 **시세 · 증권사 투자의견/레포트 · 시황(뉴스) · 재무제표**를
**한 장의 리포트**처럼 보여주는 단일 HTML 대시보드입니다. 빌드 도구 없이 `index.html` 하나로 동작합니다.

## 화면 구성

| 섹션 | 내용 |
|------|------|
| **종목 요약** | 종목명·코드·시장(KOSPI/KOSDAQ), 현재가·등락, 시가총액, PER/PBR/EPS, **조회 기준 시각** |
| **시세 · 기술적지표** | 가격 차트(1M/3M/6M/1Y) + **이동평균 MA5/20/60** + **RSI(14)** + 거래량, 52주 최고/최저, **지수 대비 초과수익률** |
| **외국인 · 기관 수급** | 일별 순매수 대금(외국인/기관) 차트 + 외국인 지분율 추이, 5일/20일 누적 순매수 |
| **증권사 투자의견** | 목표주가 밴드(최저·평균·최고 vs 현재가), 상승여력, 매수/중립/매도 의견분포, 최근 레포트 목록 |
| **시황 · 뉴스** | 종목 관련 최신 뉴스 헤드라인 |
| **재무제표** | 연간 손익(매출·영업이익·순이익) 차트 + 표, 재무상태(자산·부채·자본), ROE·부채비율 |

### 주요 기능
- **증권사 리포트 매일 자동 요약(📰)** — 아래 「증권사 리포트 다이제스트」 참고
- **관심종목 즐겨찾기(★)** — 브라우저에 저장(localStorage), 상단 칩에서 원클릭 조회
- **종목 비교(⇄)** — 최대 4종목을 기준=100 리베이스 차트 + 지표 표로 비교
- **지수 대비 보기** — 가격/지수대비(KOSPI·KOSDAQ 리베이스) 토글, 초과수익률 표시
- **PDF 저장/출력(🖨)** — 화면 그대로 A4 리포트로 저장·인쇄(`@media print`)
- 라이트/다크 테마 전환(◐), 종목명 자동완성, 6자리 코드 직접 입력

## 실행 방법

### 방법 1) 단일 파일 (가장 간단)

`standalone.html` **한 파일**에 CSS·JS·차트 라이브러리·데이터가 모두 인라인되어 있습니다.
별도 서버 없이 파일을 브라우저로 열기만 하면(더블클릭) 바로 동작합니다.

```
standalone.html  ← 이 파일만 열면 됨
```

### 방법 2) 분리 파일 + 로컬 서버 (개발용)

`index.html`은 `data/*.js`, `vendor/*.js`를 외부에서 로드하므로 로컬 서버로 열어야 합니다
(파일 프로토콜로 열면 브라우저 보안정책에 막힐 수 있음).

```bash
# 저장소 루트에서
python3 -m http.server 8000
# 브라우저에서 http://localhost:8000 접속
```

> `standalone.html`은 `index.html` + `data/*.js` + `vendor/chart.umd.js`를 합쳐 생성한 산출물입니다.
> 소스를 수정할 때는 `index.html` / `data/*.js`를 고친 뒤 다시 합치면 됩니다.

## 증권사 리포트 다이제스트 (매일 자동 요약)

`docs/reports/index.html` — **그날 나온 증권사 리포트를 모아 요약해 보여 주는 화면**입니다.
대시보드 상단의 **📰 리포트 요약** 단추로 들어갑니다.

```
GitHub Actions(증권사 리포트 수집)  ─매일 08:40 · 17:10 KST→  data/reports/latest.json
                                                                    │
                                                    docs/reports/index.html 이 읽어 그림
```

| 무엇 | 어디서 |
|---|---|
| 리포트 목록 | **네이버 리서치** 여섯 판(종목분석 · 산업분석 · 시황정보 · 투자정보 · 경제분석 · 채권분석) + **미래에셋증권 리서치**(리서치 리포트 · 글로벌 리서치) + **하나증권 리서치** |
| 해외 리포트 | 미래에셋 **글로벌 리서치** 판 전체, 그리고 티커 꼬리표가 붙은 줄(`NVDA.US` · `688017.CH` · `00981 HK`) — 카드에 **해외** 딱지가 붙습니다 |
| 서두 총평 | 그날 판·한 주 판 머리의 **「한눈에」** — 건수 · 갈래 · 주제 · 목표주가 · 겹친 종목을 문장으로 엮은 것 |
| 논점 브리핑 | 총평 아래 **주제별 실제 리포트 문장** — 어느 증권사가 무엇을 말했는지, 눌러서 원문으로 갑니다 |
| 요약 | **리포트 본문에서 원문 문장 여섯을 골라** 이은 추출 요약 (`scripts/fetch_reports.py`) — 판단·실적·전망·위험에 몫을 나눠 뽑습니다. 본문은 네이버 모바일 상세 API(`/api/research/{갈래}/{id}`)에서 받습니다 |
| 핵심 수치 | 본문에 **적혀 있는** 상승여력·목표배수·밸류에이션을 그대로 옮긴 것 (셈은 하지 않습니다) |
| 주간 인기 | 지난 이레치를 합쳐 **조회수 순 18장** + 주간 셈(건수·증권사·목표주가 상하향·많이 다뤄진 종목) |
| 목표주가 · 투자의견 | 상세 API 가 **칸으로** 줍니다(`goalPrice` · `prevGoalPrice` · `opinion`). 상하향은 목표가와 직전 목표가를 견주어 가리고, 두 수를 나란히 남겨 눈으로 확인할 수 있게 합니다. 칸이 비었을 때만 본문에서 정규식으로 캡니다(「목표주가 37만원」 같은 만·억 단위까지 환산) |
| 애널리스트 실명 | 미래에셋 리서치 목록 (네이버에는 없는 값) |
| 세부 리포트 | 카드를 누르면 **네이버 상세**, 「원문 PDF ↓」는 **증권사 PDF**, 「미래에셋 원문 ↓」은 **하우스 원문** |

### 출처를 셋으로 두는 까닭

같은 리포트가 두 곳에 다 있으면 **한 줄로 합칩니다** — 네이버 쪽에는 본문 요약이,
하우스 쪽에는 애널리스트 실명과 원문 PDF가 있어 둘 다 아깝기 때문입니다.
미래에셋·하나에만 있는 것(해외 종목 리포트 등)은 새 줄로 섭니다.

**증권사 자체 게시판은 열한 곳을 찔러 둘만 열렸습니다** — 미래에셋과 하나증권입니다
(삼성 · NH · 한국투자 · 유안타 · 메리츠 404, KB 500, 대신 403, 키움은 빈 쪽).
하나 쪽은 표가 아니라 `<ul><li>` 얼개라 앞선 탐색에서 빈 쪽으로 보였습니다.

네이버 목록은 **모바일 JSON API**(`m.stock.naver.com/api/research/*`)로 받습니다.
HTML 표를 긁는 것보다 튼튼하고 제목이 잘려 오지 않습니다. API가 막히면 예전
HTML 표 파서로 그대로 내려앉습니다.

> 붙여 보고 접은 곳 — **한경 컨센서스**는 http·다른 호스트·다른 얼개까지 넷 다 HTTP 500,
> **한국IR협의회**는 세 길 모두 시간 초과, **다음 금융**은 500/404,
> **KRX 기업분석보고서**는 404 였습니다. 네이버에는 해외 리서치 API 길이 없습니다
> (`global` · `overseas` · `world` 모두 404).
> `scripts/probe_reports.py` 로 러너에서 확인했고, 살아나면 같은 자리에 붙입니다.

> **외국계 IB(골드만 · 모건스탠리 · JP모건 등)의 한국물 리포트는 넣지 못했습니다.**
> 기관 전용이라 공개 목록이 없습니다. 지금 「해외」로 잡히는 것은 **국내 증권사가
> 해외 기업·업종을 다룬 리포트**입니다 — 다른 것이니 섞어 읽지 마십시오.

화면에서 할 수 있는 것 — **조회**(종목명·종목코드·증권사·애널리스트·제목, 자동완성 딸림),
판별·증권사별 걸러 보기, **인기순(기본)**/최신순/목표주가 변경순 정렬, 「본문 발췌」 펼쳐 보기,
종목명 옆 **종목 대시보드**로 이동(`index.html?code=005930`), 지난 날짜 판 다시 보기.

종목으로 조회하면 그 종목이 **한 줄로 섭니다** — 몇 곳이 다뤘는지, 목표주가 평균·최저·최고,
투자의견 분포. 조회하는 동안 「오늘의 주요 리포트」는 접혀 결과가 화면 위로 올라옵니다.

**요약은 새로 쓴 문장이 아니라 원문 문장을 고른 것입니다.** 러너에는 모델이 없어
문장을 짓지 않습니다 — 지어낸 요약이 리포트 자리에 앉는 것보다 원문 여섯 줄이
안전하기 때문입니다. **PDF 로만 보는 사람은 「세부 리포트」를 누를 수 없으므로**
카드만 읽고도 요지가 잡히도록 여섯 줄까지 싣고, 첫 줄(대개 판단)은 굵게 세웁니다.
길이만 늘리면 같은 말이 되풀이되므로 갈래별로 몫을 나누고, 제목과 겹치는 문장과
서로 닮은 문장은 버립니다. 목표주가·투자의견도 기계가 뽑은 값이라 원문과 다를 수 있으니,
판단은 반드시 세부 리포트 원문으로 하십시오.

### 서두에 「무슨 이야기인지」를 싣는 까닭

「한눈에」는 처음에 **몇 건인지만** 말했습니다 — 74건, 시황이 21건, 주제는
금리·반도체. 정작 알고 싶은 것은 무슨 이야기인가입니다.

그래서 총평 아래에 **논점 브리핑**을 답니다. 주제마다 그 주제를 다룬 리포트를
모아, 가장 많이 읽힌 것부터 판단 문장을 **증권사·종목과 함께 그대로** 옮깁니다.
지어낸 문장이 아니라 리포트가 한 말이고, 눌러서 원문으로 갑니다. 목표주가를
움직인 건에는 그 까닭 한 줄을, 여러 곳이 함께 본 종목에는 증권사별 한 줄을
붙여 시각차가 드러나게 합니다.

고르는 데 걸린 것 셋을 막아 두었습니다.

- **시황 리포트 한 건이 여러 주제에 걸립니다.** 금리·반도체·금융에 같은 줄이
  세 번 실렸습니다 — 주제를 넘나들며 겹치지 않게 합니다.
- **시세 나열이 뽑힙니다.** 「KOSPI 6,912pt (+1.53%), KOSDAQ 837pt」 같은 줄은
  주제 이야기가 아닙니다 — 글자가 절반은 되어야 읽을 거리로 칩니다.
- **목표주가 줄이 두 번 실렸습니다.** 그 줄이 그날 가장 중요한 대목이니
  목표주가 쪽이 먼저 집고, 주제 쪽은 다른 목소리로 채웁니다.

### 주간 인기 리포트

그날 판만 보면 그 주의 화두를 알 수 없습니다 — **오늘 올라온 리포트는 아직 아무도
읽지 않았기 때문**입니다. 조회수는 날이 갈수록 쌓이므로 인기 목록은 자연히 며칠 전
것으로 채워지고, 그게 맞습니다.

한 판에 담기는 것은 네이버 목록의 앞쪽 몇 쪽뿐이라 엿새 전 리포트는 이미 밀려나
없습니다. 그래서 `data/reports/<날짜>.json` 으로 남겨 둔 **지난 판들을 합쳐** 이레를
채웁니다(같은 리포트는 조회수가 큰 쪽과 요약이 있는 쪽을 남깁니다).

주간 상위는 **본문을 먼저 엽니다** — 갈래마다 몫을 주어 도는 탓에 경제분석·시황정보의
주간 상위가 번번이 본문 열기 상한 밖으로 밀렸습니다(열여덟 장 중 일곱 장).

### 재검산 — 실린 숫자와 문장을 원자료에 대고 맞춘다

```bash
python3 scripts/verify_reports.py data/reports/latest.json
```

수집 워크플로가 판마다 돌려 `data/reports/verify.txt` 에 남깁니다. 어긋난 것이
있으면 나가는 값이 1 입니다 — **산출물을 내기 전에 여기부터 봅니다.**

무엇을 보는가.

| 갈래 | 보는 것 |
|---|---|
| 가. 수집 | 빠진 칸 · 주소 중복 · 날짜꼴 · 수집일보다 뒤인 날짜 · 조회수 |
| 나. 셈 | 전체·그날 건수, 갈래·원천·증권사별 건수, 주제 건수, 목표주가 상하향, 겹친 종목 — **실린 값과 다시 센 값이 같은가**. 머리 요약 *문장에 박힌 숫자*까지 본다 |
| 다. 인용 | 요약이 **본문 문장만으로 되짚어지는가**, 첫 줄이 요약 안에 있는가, 수치 조각과 목표주가가 원문에 적힌 그대로인가, 브리핑 인용이 그 리포트에서 왔는가. 목표주가가 **칸에서 온 것**은 잣대가 달라, 직전 목표가와 견주어 방향이 두 수와 맞는지를 봅니다 |
| 라. 오염 | 첨부파일명·컴플라이언스 머리글·사이트 길잡이줄·연락처·마크업 부스러기 |
| 마. 출처 | 모든 주소가 알려진 원문 서버인가, 「해외」 딱지에 근거가 있는가 |
| 바. 주간 | 스냅숏을 다시 합쳐 센 건수, 기간 밖 유입, 조회수 내림차순, 주간 브리핑 인용 |
| 사. 원천 | 죽은 원천이 있는가, 산 원천이 둘 이상인가, 그날 자가 있는가 — 반쯤 받았거나 끊겼다 살아난 원천도 적는다 |
| 아. 추출 | 연 본문에서 요약이 나왔는가, 그날 자에 요약이 붙었는가, 수집기가 남긴 경고가 있는가 |

**사·아 는 「없는 것」을 보는 묶음입니다.** 가~바 는 실린 것을 대조하므로, 자료가
통째로 빠지면 대조할 것이 없어 조용히 통과합니다. 실제로 두 번 그랬습니다 —
하나증권이 죽어 쉰 줄이 사라진 판에서 검사 서른넷이 모두 통과했고(→ 사),
네이버가 상세 페이지를 갈아엎어 요약이 **한 건도** 안 나온 판에서 서른일곱이
모두 통과했습니다(→ 아). 빠진 자료는 지어낸 수치와 다른 종류의 흠이고, 그래도
내겠다면 사람이 알고 내야 합니다.

되짚기(다)가 이 검산의 핵심입니다. 요약을 문장 부호로 잘라 본문에서 찾으면 안
됩니다 — 요약은 본문의 **떨어진 자리**에서 고른 문장을 이어 붙인 것이라, 마침표
없이 끝나는 소제목 뒤에 다른 대목이 붙으면 한 덩이로 보입니다. 그래서 본문을
수집기와 **똑같은 규칙**으로 잘라 문장 꾸러미를 만들고, 요약을 그 꾸러미만으로
쌓아 올려 봅니다. 한 글자라도 남으면 그 자리에서 걸립니다.

이 검산이 증명하는 것과 못 하는 것을 갈라 둡니다. **증명합니다** — 인쇄되는 셈이
실린 목록과 맞고, 인쇄되는 문장·수치가 리포트에 글자 그대로 있고, 모든 항목에
원문 주소가 달려 있음. **증명하지 않습니다** — 증권사가 한 말이 맞는지. 그건 이
도구의 일이 아니며, 카드마다 원문 주소를 다는 까닭입니다.

첫 판에서 둘이 걸렸습니다.

- **하나증권 카드 마흔여덟 장이 모두 같은 곳을 가리켰습니다.** 목록 쪽에 리포트마다
  열리는 주소가 없어 걸개 주소를 넣어 둔 탓입니다. 내려받기 주소가 곧 그 리포트이니
  그것을 원문 자리로 삼습니다.
- **한 주 셈이 한 건 적었습니다.** 무더기를 `nid` 하나로만 갈랐는데 원천마다 번호를
  따로 매깁니다 — 네이버의 95903 과 다른 곳의 95903 이 한 칸을 다투었습니다.
  원천을 붙여 가릅니다(`pool_key`).

늘 남는 참고 두 가지. **조회수는 네이버에만 있습니다** — 미래에셋·하나 제 목록에는
없는 값이라 그 줄들은 인기순에서 맨 뒤로 밀립니다. 그리고 본문은 앞 1200자만
보관하므로 그 뒤에서 온 문장은 **대조하지 못한 것으로 따로 셉니다**(했다고 세지
않습니다).

### 건네줄 파일 만들기 — 한 파일 HTML + PDF 셋

```bash

bash scripts/make_reports_outputs.sh 2026-08-15 # 그날 판
```

`out/` 아래에 넷이 생깁니다(`.gitignore` 에 있습니다).

| 파일 | 무엇 |
|---|---|
| `미래에셋_증권사리포트_YYYYMMDD.html` | **데이터까지 넣은 한 파일** — 서버 없이 더블클릭하면 열리고 조회·걸러 보기가 다 됩니다 |
| `…_요약.pdf` | 머리 요약 · 주요 리포트 12장 · 목표주가를 움직인 리포트 (2쪽 안팎) |
| `…_주간인기.pdf` | 주간 셈 · 많이 다뤄진 종목 · **조회수 순 18장** (2쪽 안팎) |
| `…_전체.pdf` | 위의 것 + 주간 + 전체 목록 (40쪽 안팎) — **차례**와 **갈래별 묶음**이 들어갑니다 |

PDF 에서도 제목과 「원문 PDF」는 눌러서 원문으로 갑니다. 화면의 조회창·걸개·
단추는 인쇄에서 빠지고, 카드는 쪽 경계에서 잘리지 않으며, 다크 테마여도
종이는 늘 밝은 바탕으로 나옵니다.

> 인쇄에서는 카드를 격자가 아니라 **흐르는 단**으로 놓습니다. 격자는 쪽 경계에서
> 제대로 쪼개지지 않아, 요약을 여섯 줄로 늘리자 마지막 줄의 카드가 꼬리말 위로
> 넘쳐 겹쳤습니다.

#### 언제 저절로 도는가

예약은 평일 일곱 판입니다 — 본판 넷(08:40 · 09:25 · 13:00 · 17:20)과 예비
셋(10:10 · 14:20 · 18:40). 예비를 둔 까닭은 **GitHub 예약이 제때 오지 않기**
때문입니다. 9/14 에는 네 판 모두 **65~74분 늦게** 돌았고, 슬롯이 통째로 흘러
없어진 날도 있었습니다. 둘 다 돌아도 손해가 없습니다 — 값이 같으면 커밋
단계가 「변경 없음」으로 넘어가 빈 커밋이 남지 않습니다.

아침 배포는 예약에 기대지 않습니다. 평일 **09:25 KST** 에 Routine 이 깨어나
`request_reports_refresh.sh` 로 **수집을 직접 부르고** 끝나기를 기다린 뒤,
검산을 돌리고 배포본을 만듭니다. Routine 은 초 단위로 정확히 오고(09:25:11 ·
09:35:47 · 09:35:37), 밀어넣기로 깨운 수집은 2~3분이면 끝납니다 — 아침
길목에서 늦는 쪽(예약)을 뺀 것입니다. 예약 판은 그래도 남겨 둡니다: Routine
이 못 도는 날의 그물입니다.

> **Routine 은 기존 세션에 붙여야 합니다.** 판마다 새 세션을 띄우는 꼴로
> 걸었더니 9/16 에 제때(09:25:11) 깨어나 19분을 돌고도 **커밋을 하나도 밀지
> 못했습니다** — 어느 갈래에도 자국이 없습니다. 예약이 새로 띄우는 세션에는
> 저장소에 밀어 넣을 자격이 없는 것으로 보이며, 다른 작업의 예약에도 같은
> 관찰이 적혀 있습니다(2026-09-15). 밀지 못하면 수집을 부를 수 없으니 그날
> 아침이 통째로 빕니다. 기존 세션에 붙인 예약들은 같은 날에도 정상으로
> 밀었습니다. 그래서 이 Routine 도 세션에 붙여 다시 걸었습니다.

## 데이터 소스

무료 공개 소스를 우선 사용하고, 실패 시 **섹션별로 샘플 데이터로 폴백**합니다.
각 섹션에는 `실시간` / `샘플` 배지가 표시됩니다.

| 섹션 | 실시간 소스 | 폴백 |
|------|-------------|------|
| 시세/현재가/차트 | **네이버 모바일 `m.stock.naver.com/api`** 우선, Yahoo `chart` 보조 | 내장 샘플 |
| 외국인/기관 수급 | 네이버 `api/stock/{code}/trend` | 내장 샘플 |
| 지수(KOSPI/KOSDAQ) | Yahoo `chart/^KS11 · ^KQ11` | 내장 샘플 |
| 재무제표 | Yahoo `quoteSummary` (손익/재무상태) | 내장 샘플 |
| 투자의견/목표주가 | Yahoo `quoteSummary` (financialData, recommendationTrend) | 내장 샘플 |
| 시황/뉴스 | Google News RSS(`news.google.com/rss/search`) | 내장 샘플 |
| 증권사 레포트 목록 | 네이버 금융 리서치 (러너가 매일 수집 → `data/reports/`) | 예시 데이터 + 네이버 리서치 딥링크 |

모든 소스는 **병렬 호출 + 4초 타임아웃**으로 요청하며, 실패한 섹션만 개별적으로 샘플로 대체합니다(전체 화면은 항상 정상 렌더). 요약 헤더에 조회 기준 시각과 출처가 표시됩니다.

> 증권사 원문 리포트(PDF)는 공개 API가 없어, 목록은 예시로 채우고
> [네이버 금융 리서치](https://finance.naver.com/research/)로 연결되는 딥링크를 제공합니다.

### 브라우저 CORS 안내

순수 브라우저(단일 HTML)에서 위 API를 직접 호출하면 **CORS로 차단**되는 경우가 많습니다.
이를 위해 `index.html`의 `PROXIES` 배열에 **CORS 프록시 폴백**이 설정되어 있습니다.

```js
var PROXIES = [
  function (u) { return u; },                                              // 1) 직접 호출
  function (u) { return "https://corsproxy.io/?url=" + encodeURIComponent(u); },      // 2) 프록시
  function (u) { return "https://api.allorigins.win/raw?url=" + encodeURIComponent(u); } // 3) 프록시
];
```

- 사내망/폐쇄망 등으로 외부 접근이 막히면 세 경로 모두 실패하고 **샘플 데이터**로 표시됩니다(화면은 항상 정상 렌더).
- 안정적인 실시간 연동이 필요하면, 자체 백엔드 프록시(예: `/api/proxy?url=...`)를 만들어 `PROXIES`에 추가하는 것을 권장합니다.
- 미래에셋 **사내 API**가 있다면 `fetchYahoo` / `fetchNews`를 사내 엔드포인트 호출로 교체하면 됩니다.

## 데이터 수집 (매일 자동)

미래에셋증권 홈페이지는 **WebSquare 기반 SPA**이고, 데이터는 `.wjson` POST 엔드포인트로
오갑니다. 정적 HTML에는 상품 정보가 전혀 없어 **헤드리스 브라우저 렌더링**이 필요합니다.
따라서 수집은 GitHub Actions 러너에서 Playwright 로 수행합니다.

| 파일 | 역할 |
|------|------|
| `.github/workflows/els-weekly.yml` | **매일 08:00 KST** 수집 → `data/els.js` 갱신 → 단일 파일 재빌드 → 커밋 |
| `scripts/collect_els.mjs` | 실제 수집기. 상품 목록 화면을 렌더링하고 `.wjson` 응답에서 상품을 추출 |
| `.github/workflows/els-discover.yml` | 사이트 구조 조사용(1회성). 엔드포인트가 바뀌었을 때 다시 돌린다 |
| `scripts/discover_els.mjs` | 위 조사 스크립트 |
| `scripts/collect_history.mjs` | 기초자산 10년치 일별 종가(Yahoo Finance) → `data/els.js` 의 `history` |
| `tools/discovery/rendered_list.json` | 수집할 때 홈페이지 화면에 실제로 그려진 목록 원문. 수집 결과와 대조용 |
| `scripts/reparse_els.mjs` | 파서를 고쳤을 때, 이미 수집된 `data/els.js` 의 일정을 원문 표기에서 다시 계산 |

**위험등급**은 목록 API 응답에 없습니다(`omkt_drvs_risk_gcd` 는 사내 코드값). 화면에만
"매우높은위험" 같은 문구로 렌더링되므로, 수집기가 그려진 표에서 상품명과 함께 읽어
`riskLabel`(원문) / `riskGrade`(1~6) 로 저장합니다.

**과거 시세**는 상품 수집과 분리된 단계입니다. 한쪽이 실패해도 다른 쪽 데이터는
그대로 유지되고, 새 기초자산이 등장했는데 심볼 매핑이 없으면 그 자산만 건너뛰며
`history.missing` 에 남습니다(해당 상품은 과거 시뮬레이션을 표시하지 않습니다).
매핑은 `scripts/collect_history.mjs` 의 `SYMBOLS` 에 추가합니다.

배리어 시퀀스는 홈페이지 원문 표기(`structureDesc`)에서 뽑습니다. 파서를 손봤다면
다음 주 수집을 기다리지 말고 `node scripts/reparse_els.mjs` 로 기존 데이터를 맞춰두세요
(수집기와 같은 파서를 씁니다).

ELS 청약기간은 보통 1주일이라 주 1회 수집으로는 이미 마감된 상품이 며칠씩 남습니다.
그래서 **매일** 수집하고, 페이지는 저장된 청약기간과 **여는 날짜**를 비교해 청약중 /
청약마감 / 청약예정을 다시 판정합니다. 마감된 상품은 기본으로 목록에서 숨기고,
수집한 지 하루라도 지났으면 목록 위에 안내 문구와 홈페이지 링크를 띄웁니다.

**수집이 실패해도 페이지는 깨지지 않습니다.** 워크플로우는 `data/els.js` 를 건드리지 않고
끝나므로 직전 수집 데이터가 그대로 유지되고, 진단 자료는 `els-collect-debug` 아티팩트로
남습니다. 한 번도 수집되지 않은 상태에서는 내장 예시 데이터가 표시되며, 화면에
**"예시 데이터"** 배지가 붙습니다.

## ELS 데이터 스키마

`data/els.js` 는 `window.ELS_DATA` 하나를 정의합니다.

```js
window.ELS_DATA = {
  updatedAt: '2026-08-04T00:00:00Z',  // 수집 시각. null 이면 "미수집"
  source: 'live',                     // 'live' | 'sample'
  sourceNote: '...', sourceNoteEn: '...',
  products: [{
    code: 'ELS31234',
    name: '미래에셋증권 ELS 제31234회',
    type: 'ELS',                      // ELS | ELB | DLS | DLB
    underlyings: ['KOSPI200', 'S&P500'],
    couponRate: 8.4,                  // 세전 수익률 %. 기준은 rateBasis 가 정한다
    rateBasis: 'annual',              // 'annual' = 연율 | 'total' = 만기 기준 총액
    maxLossRate: 100,                 // 조건 미충족 시 최대손실률 %
    maturityMonths: 36,
    schedule: [                       // 조기상환 평가 일정
      { months: 6,  barrier: 90 },    // barrier = 최초기준가격 대비 %
      { months: 12, barrier: 85,      // 리자드 회차면 아래 두 필드가 붙는다
        lizard: 45, lizardRate: 20.5 },//  barrier 를 못 채워도 45% 이상이면 상환
      { months: 36, barrier: 75 },    // 마지막 항목이 만기
    ],
    knockIn: 50,                      // 낙인 배리어 %. null 이면 노낙인
    principalProtection: 0,           // 원금지급률 %. 100 이면 ELB
    riskGrade: 2,                     // 1(매우높은위험) ~ 6(매우낮은위험). 화면에서 수집
    riskLabel: '높은위험',             // 홈페이지 표기 그대로. 없으면 null
    offerStart: null, offerEnd: null, issueDate: null,
    minAmount: 1000000,
    url: null,                        // 상품 상세 링크
  }],

  // 과거 시뮬레이션용 기초자산 시세 (scripts/collect_history.mjs)
  history: {
    dates:  [20160803, 20160804, ...],        // 공통 거래일 축 (전 자산 합집합)
    series: { 'KOSPI200': [100, 99.8, ...] }, // 첫 유효일 = 100 으로 리베이스
    symbols:{ 'KOSPI200': '^KS200' },         // 사용한 Yahoo 심볼
    missing: [],                              // 심볼 매핑이 없거나 수집 실패한 자산
  },
};
```

`schedule` 의 **마지막 항목이 만기**이며, 회차별 누적 수익률은
`만기 총 수익률 × (months / maturityMonths)` 로 계산합니다.

> **수익률 기준** — 홈페이지 API 의 `omkt_drv_frcs_ern_r` 는 **"조건 충족시 연 수익률(세전)"의
> 최대치**입니다. 홈페이지 화면의 컬럼 헤더와 표시값("최대 10.71%")으로 확인했습니다
> (`scripts/verify_rate_basis.mjs`). 원금지급형 ELB 도 10%대가 나오는데, 월지급 쿠폰이
> 조건부라 "최대" 연율일 뿐 확정 수익이 아니기 때문입니다.
> 페이지는 이를 **상한**으로 명시하고 연율과 만기 보유 시 총액을 함께 보여줍니다.
> `couponAnnual` 만 있는 예전 데이터는 연율로 해석합니다.

## 과거 시뮬레이션

투자설명서의 "과거 시뮬레이션(모의실험)"과 같은 방식입니다. 과거 기초자산 종가로
**이 상품이 매 거래일 발행되었다고 가정**하고, 회차별 조기상환 판정과 낙인 터치를
그대로 돌려 결말을 셉니다.

| 항목 | 기준 |
|------|------|
| 판정 가격 | 일별 **종가**. 기초자산이 여럿이면 워스트 퍼포머 |
| 조기상환 | 평가일(발행일 + n개월) 이후 첫 거래일 종가가 배리어 이상이면 상환 |
| 리자드 | 배리어는 못 채웠지만 리자드 선 이상이면 리자드 수익률로 상환 |
| 낙인 | 기간 중 종가가 한 번이라도 낙인 아래로 내려가면 터치 |
| 만기 미충족 | 낙인 미터치면 약속 수익, 터치했으면 하락률만큼 손실. 원금지급형은 0% |
| 발행일 범위 | 시세 시작일 ~ (시세 마지막 날 − 만기). 만기까지 관찰 가능한 날만 |
| 제외 | 세금·수수료·중도상환 비용 |

> **설명서 수치를 옮긴 것이 아니라 이 페이지가 계산한 값입니다.** 데이터 출처
> (Yahoo Finance 종가)와 가정이 발행사 설명서와 달라 수치가 일치하지 않을 수 있습니다.
> 고객 대상으로 쓸 경우 설명서 수치와의 차이를 반드시 확인하세요.

## 유의사항 (ELS 페이지)

이 페이지는 상품 **구조 이해를 돕기 위한 참고자료**이며 투자 권유나 청약 안내가
아닙니다. 모든 수치는 세전 기준이고, 시뮬레이터 결과는 이용자가 입력한 가정에 따른
산술 계산일 뿐 미래 수익을 예측하지 않습니다. 실제 상품 조건은 각 상품의 투자설명서가
우선합니다.

> **사내 활용 시 확인 필요** — 실제 판매 중인 상품 정보를 고객에게 노출하는 화면은
> 금융투자협회 광고 심의 및 사내 컴플라이언스 검토 대상일 수 있습니다.

| 상단 요소 | 하는 일 |
|-----------|---------|
| **상태줄** | 무엇을 언제 받은 값으로 보고 있는지(`실시간 스트리밍 수신 중` / `가격 12분 전`), 미국 장이 열려 있는지(`정규장 · 미 동부 10:32` / `장 마감 · 개장까지 6시간 12분`). 장중인데 가격이 15분 넘게 묵으면 **지금 수집 요청** 링크가 붙습니다(Actions 에서 수집을 직접 돌립니다) |
| **자동 갱신** | **처음에는 꺼져 있습니다.** 켜면 1분마다 가격 파일을 다시 확인해 표가 스스로 따라갑니다(탭이 숨어 있으면 부르지 않고, 탭으로 돌아오면 즉시 한 번 확인). 꺼 두면 화면을 연 시점의 값이 그대로 남고 갱신은 `지금 새로 조회`를 누를 때만 합니다. 켜 두면 그 파일에서 계속 기억합니다 |
| **지금 새로 조회** | 캐시를 버리고 **이 브라우저가** 모든 경로를 다시 시도합니다(스트리밍 재접속 → 직접 조회 → 러너 파일 재다운로드). 수집을 새로 돌리는 것이 아니라 *이미 올라와 있는 가장 새 값*을 받아옵니다. 끝나면 **무엇이 갱신됐는지** 상태줄에 7초간 알려 줍니다 — `실시간 스트리밍이 살아 있습니다` / `브라우저에서 직접 받았습니다` / `러너가 올린 새 가격을 받았습니다(3분 전 수집)` / `새로 올라온 값이 없습니다` |
| **지금 수집 요청** (상태줄 링크) | **서버(GitHub Actions 러너)가 새로 받아오게** 하는 링크입니다. 가격 파일이 15분 넘게 묵었고 미국 장이 열려 있을 때만 나타납니다. 눌러 열린 페이지에서 **Run workflow** 를 누르면 30~60초 뒤 새 파일이 올라오고, 그 다음 **지금 새로 조회**로 받아 갑니다. 브라우저가 야후에 직접 붙지 못하는 사내망에서는 **새 값을 만드는 유일한 방법**입니다 |

> 지금 수집 요청은 *서버가 야후에서 새로 받아오게 하는* 동작입니다. CSV 내려받기는 조회와 무관하게 화면의 표를 파일로 저장합니다.

값이 바뀐 가격 칸은 잠깐 물들어(상승 붉게 / 하락 파랗게) 갱신이 실제로 일어났는지 눈으로 확인됩니다.

### 우리 망에서 막히는지 확인하는 방법

⑩ **데이터 출처 · 조회 진단** 섹션의 **연결 점검 — 우리 망에서 막히나?** 버튼을 누르면, 이 브라우저에서
경로마다 실제로 한 번씩 불러 보고 결과를 표로 적습니다(10초 이내, 읽기만 하며 아무것도 저장하지 않습니다).

| 경로 | 막히면 어떻게 되나 |
|---|---|
| **수집 파일**(`raw.githubusercontent.com`) | 이 화면의 주된 경로. **여기만 열리면 전부 정상**입니다 |
| **야후 직접 조회**(`query1.finance.yahoo.com`) | 막혀도 위 경로로 자동 대체 — 신경 쓸 필요 없음 |
| **실시간 스트리밍**(`wss://streamer.finance.yahoo.com`) | 막혀도 위 경로로 자동 대체 — 초 단위 갱신만 없어짐 |
| **사내 프록시 / 사내 폴더** | ⑩ 에 주소를 넣어 둔 경우에만 함께 점검합니다 |

막힘은 이유를 구별해 적습니다 — 사내 담당자에게 물어볼 말이 달라지기 때문입니다:
`연결이 거부됐습니다(방화벽 차단이거나 CORS 거부)` / `응답 없음(8초, 조용히 버리는 형태)` /
`407 사내 프록시가 로그인을 요구합니다` / `403 프록시나 서버가 거부` / `404 주소에 파일이 없습니다(차단이 아님)`.
아래 **결과 복사** 버튼으로 브라우저·주소까지 담은 요약을 복사해 담당자에게 그대로 보낼 수 있습니다.

버튼을 누르지 않고 눈으로 보는 방법도 있습니다 — **화면 위쪽 배지**입니다.
`실시간` · `시세 N분 전` · `스냅샷 09.08 21:17` 중 하나면 값이 들어오고 있고,
전부 `예시 데이터`로 나오면 모든 경로가 막힌 것입니다(상태줄에도 `예시 데이터 — 실제 시세가 아닙니다`가 뜹니다).

화면 구조 확인용 예시 값을 만들어 채우고, 그 사실을 배지(`예시 데이터`)·상태줄·안내 상자에 밝힙니다.
**업무에 쓰면 안 됩니다** — 그 PC 에서는 `us-top100-offline.html`(데이터 내장)을 쓰세요.

### 어느 기능을 써야 하나 (평소 / 오프라인 PC)

**평소(인터넷 되는 PC)** — 화면을 열면 그 시점의 값이 한 번 들어옵니다. 그 뒤로는 `지금 새로 조회`를
필요할 때 누르면 됩니다(회의 직전처럼 *지금 이 순간의 값*을 확실히 받고 싶을 때). 장을 계속 지켜보는
자리라면 **자동 갱신**을 켜 두세요 — 1분마다 새 파일을 확인해 표가 스스로 따라갑니다. 처음부터 켜 두지
않는 이유는, 읽고 있던 숫자가 눈앞에서 바뀌면 방금 본 값과 어긋나기 때문입니다.
`지금 수집 요청`은 미국 장중인데 상태줄이 15분 넘게 묵어 있을 때만(그 링크는 그때만 나타납니다) 쓰면 됩니다.

**인터넷이 안 되는 업무용 PC** — 세 기능 모두 **아무 효과가 없습니다**. 브라우저는 `file://` 로 열린
페이지가 *옆에 있는 json 파일*을 읽는 것조차 CORS 로 막기 때문에(origin `null`), 데이터를 같이
복사해 두어도 소용이 없습니다. 그 PC 에서는 **데이터를 파일 안에 넣은 단일 파일**을 써야 합니다:

**가장 쉬운 길 — 고정 주소에서 바로 받기.** 매일 수집이 새 판을 이 주소에 올려 둡니다
(열고 **다른 이름으로 저장**):

    https://raw.githubusercontent.com/hanaroline/work_1/us100-data/data/us100/us-top100-offline.html

직접 만들 수도 있습니다:

```bash
# 인터넷 되는 PC 에서 (데이터가 저장소에 있는 상태)
git checkout origin/us100-data -- data/us100      # 최신 수집분 받기
python scripts/make_offline_html.py               # → us-top100-offline.html (약 4.3 MB)
```

**GitHub Actions 의 수집 실행 페이지 → Artifacts → `us-top100-offline`** 에도 같은 파일이
올라가지만, 그쪽은 로그인해서 zip 을 풀어야 하고 14일 뒤 사라집니다. 위 고정 주소는 늘
가장 새 판입니다. 이 파일 하나만 업무용 PC 로 옮겨 더블클릭하면 100개 기업의 시세·지표·
실적·컨센서스·일정·뉴스·차트·종목비교가 **인터넷 없이 그대로** 나옵니다.

| 쓸 파일 | `us-top100.html` | `us-top100-offline.html` |
| 자동 갱신 | 장을 지켜볼 때 켜세요 (기본 꺼짐) | 효과 없음(켜도 달라지지 않습니다) |
| 지금 새로 조회 | 필요할 때 | 효과 없음(눌러도 화면은 그대로 유지됩니다) |

### 값이 몇 시간 전 것으로 보일 때

미국 정규장은 한국 시간 밤 10:30~새벽 5:00(서머타임 기준)입니다. 그 밖의 시간에는 정규 가격이
**종가에서 멈춰** 있어 아무리 갱신해도 값이 바뀌지 않습니다. 그래서 화면은

- 히어로의 `시세 기준 …` 옆에 **왜 안 바뀌는지**를 함께 적습니다 — `· 프리마켓 (정규장 개장까지 3시간 16분)`,
- **가격 파일이 스냅샷보다 오래되면 쓰지 않습니다.** 두 파일은 따로 도착하고 예약이 밀리면 순서가 뒤집히는데,
  그때 오래된 파일로 덮으면 더 새 값이 헌 값으로 바뀝니다(먼저 도착해 이미 들어간 값도 물립니다),
- 프리마켓·애프터마켓에도 30분 주기로 수집해 **시간외 호가**(`preMarketPrice` / `postMarketPrice`)를 함께 담고,
  종목 요약 헤더에 `프리마켓 $362.19 +1.20%` 로 덧붙입니다(정규 종가를 시간외 값으로 바꾸지는 않습니다).

주소에 종목이 남습니다(`us-top100.html#NVDA`) — 링크로 특정 종목을 바로 열거나 공유할 수 있고,
새로고침해도 그 종목으로 돌아옵니다. 관심종목·선택 종목·비교 담은 종목·비교 조합·비교 기간·보조지표·언어·자동 갱신·스트리밍 설정은
브라우저(localStorage)에 남습니다.

> **처음 여는 파일은 처음 상태로 열립니다.** 브라우저는 `file://` 로 열린 로컬 HTML 을 하나의 저장소로
> 묶기 때문에, 그냥 두면 새로 받은 파일(`ustop100 (4).html`)도 이전 파일이 남긴 관심종목·비교 선택을
> 그대로 물려받습니다. 그래서 화면은 **판 문자열 + 파일 경로**를 스탬프로 남겨 두고, 스탬프가 다르면
> (= 새 판이거나 새로 받은 사본이면) 저장된 화면 설정을 지우고 시작하면서 **무엇을 지웠는지** 목록 위에
> 적습니다(`… 관심종목 · 비교 선택 설정을 지웠습니다`). 같은 파일을 계속 쓰는 동안에는 고른 것을
> 기억하고, 그때는 **무엇을 불러왔는지** 적고(`관심종목 2개 · 비교에 담은 종목 4개(…)`)
> **처음 상태로 초기화** 링크를 함께 둡니다. 같은 초기화는 ⑩ 섹션 고급 설정의 **화면 설정 전체 초기화**
> 버튼에도 있습니다. 판을 새로 내보낼 때는 `us-top100.html` 의 `var BUILD` 문자열을 함께 올립니다.
>
> 비교 섹션은 **처음 열 때 자동으로 채우지 않습니다.** 빈 화면을 피하려고 "선택 종목 + 동일 섹터 상위"로 채워 봤지만, 그러면 목록의 비교 체크박스 3개가 켜진 채 열려서 — 저장하지 않아도 — "지난번 체크가 그대로 남았다"와 똑같이 보였습니다. 지금은 아무것도 담지 않고, 비교 섹션의 **채우기 버튼**과 **기본 조합 칩**으로 안내합니다.

## 데이터 소스 — 네 경로

화면은 **가장 빠르고 확실한 것부터** 그리고, 더 신선한 값이 오면 덮어씁니다.
어느 경로로 그려졌는지는 섹션 배지가 말해 줍니다.

**⓪ 실시간 스트리밍 (WebSocket)** — `wss://streamer.finance.yahoo.com`.
**WebSocket 은 CORS 를 받지 않으므로** 정적 HTML 에서도 붙습니다. 붙으면 10분 주기 파일이
아니라 **틱 단위 실시간**으로 가격·등락률·거래량이 움직이고 배지가 `실시간 스트리밍`이 됩니다.
방화벽이 wss 를 막으면 세 번 시도한 뒤 조용히 포기하고 아래 경로가 화면을 채웁니다.

프레임은 base64 로 감싼 protobuf 라 라이브러리 없이 최소 디코더를 직접 씁니다. 잘못
디코딩한 값이 화면에 나가지 않도록 **두 가지를 검사해 통과한 틱만 반영합니다** —
① 첫 필드가 우리가 아는 심볼 문자열인지(레이아웃이 맞았다는 증거), ② 가격이 이미 아는
기준가의 ±25% 안인지. 걸러낸 건수는 ⑩ 섹션 출처 표에 그대로 나옵니다.
스트리밍은 설정에서 끌 수 있습니다.

**① 가격 파일 (장중 10분 주기)** — 스트리밍이 막힌 곳의 주 경로. `data/us100/quotes.json`. 러너가 25종목씩 묶어
4~5번 요청으로 20~40초에 받아 커밋합니다. 화면은 이 파일을 가격·등락률에 먼저 쓰고
**1분마다 다시 확인**해 새로 올라온 값을 스스로 따라갑니다. 배지에 `시세 7분 전`처럼
**실제 나이**를 적습니다(GitHub 예약은 늦을 때가 있어 주기를 약속하지 않습니다).

**② 저장 스냅샷 (하루 단위)** — `data/us100/latest.json` + `chart/{SYM}.json`.
지표·실적·컨센서스·일정·투자의견·뉴스·시계열이 들어 있습니다. 사내망·CORS 로
브라우저가 야후에 못 붙는 곳에서도 실제 수치가 나오고, 열자마자 100종목이 다 채워집니다.

**③ 실시간 (브라우저 직접 조회)** — 붙을 수 있는 환경이면 위 두 값을 덮어씁니다.
배지가 `실시간` 으로 바뀌는 것으로 구분합니다.

### 사내 프록시가 있으면 진짜 실시간이 됩니다

화면 ⑩ 섹션의 **데이터 경로 설정**에 사내 프록시 주소를 넣으면(예:
`https://intra.example.com/proxy?url={urlenc}`) 그 경로를 **가장 먼저** 시도합니다.
넣는 즉시 브라우저가 직접 야후를 호출해 지연 없는 시세를 받습니다. 스냅샷 파일 경로도
사내 주소로 바꿀 수 있습니다. 주소는 회사마다 달라 코드에 박지 않고 브라우저
(localStorage)에 저장합니다.

> 무료 공개 소스 + 정적 HTML 로 **틱 단위 실시간**을 만들 수는 없습니다(유료 피드는 키가 필요).
> 지금 구조에서 가능한 최선은 ⑴ 브라우저가 직접 붙는 환경이면 실시간, ⑵ 아니면 10분 주기
> 가격 파일, ⑶ 사내 프록시를 넣으면 다시 실시간입니다.

#### 사내 프록시가 없다면 — 개인 프록시 10줄로 만들기

Cloudflare Workers 무료 플랜에 아래를 붙여 배포하고(5분), 나온 주소를
`https://<이름>.workers.dev/?url={urlenc}` 형태로 **데이터 경로 설정**에 넣으면
그 순간부터 브라우저가 지연 없이 시세를 받습니다. 대상 호스트를 두 곳으로 못 박아
아무 주소나 대신 불러 주는 열린 프록시가 되지 않게 했습니다.

```js
const ALLOW = ['query1.finance.yahoo.com', 'query2.finance.yahoo.com', 'stooq.com'];
export default {
  async fetch(req) {
    const target = new URL(req.url).searchParams.get('url');
    if (!target) return new Response('url 파라미터가 없습니다', { status: 400 });
    let u;
    try { u = new URL(target); } catch { return new Response('주소 형식이 아닙니다', { status: 400 }); }
    if (!ALLOW.includes(u.hostname)) return new Response('허용되지 않은 호스트', { status: 403 });
    const r = await fetch(u, { headers: { 'User-Agent': 'Mozilla/5.0', Accept: 'application/json,text/plain,*/*' } });
    const body = await r.arrayBuffer();
    return new Response(body, { status: r.status,
      headers: { 'content-type': r.headers.get('content-type') || 'application/json',
                 'access-control-allow-origin': '*', 'cache-control': 'no-store' } });
  }
};
```

야후 `quoteSummary`(목표주가·컨센서스·일정)는 이 프록시로도 401 입니다 — 쿠키+crumb 이
필요하기 때문입니다. 그 항목은 계속 러너 스냅샷을 씁니다. 프록시로 살아나는 것은
**가격·차트·거래량·배당/분할·뉴스**입니다.

> **야후 `quoteSummary` 는 쿠키 + crumb 을 요구합니다(없으면 HTTP 401).** 실제로 돌려 보니
> 100종목 전부 401 이었고, crumb 핸드셰이크를 넣은 뒤 98/100 이 들어왔습니다. 이 핸드셰이크는
> 쿠키를 물고 다녀야 해서 **브라우저에서는 사실상 불가능**합니다(교차 사이트 쿠키·CORS).
> 그래서 **목표주가·컨센서스·실적발표일·투자의견·서프라이즈는 러너 스냅샷이 사실상 유일한 경로**이고,
> 브라우저 실시간 조회는 **가격·차트·거래량·배당/분할·뉴스**를 갱신하는 역할입니다.

| 항목 | 실시간 소스 | 폴백 순서 |
|------|-------------|-----------|
| 목록 시세(100종목) | **스트리밍**(wss) → Yahoo `v7/finance/quote`(크럼 필요, 브라우저에서는 대개 401) | **가격 파일(10분)** → **스냅샷** → 예시 데이터 |
| 상세 시세·일/주/월 차트·배당·분할 이벤트 | Yahoo `v8/finance/chart` (`events=div,split`) | **스냅샷**(`data/us100/chart/{SYM}.json`) → 예시 데이터 |
| 지표·실적·컨센서스·일정·투자의견 | Yahoo `v10/finance/quoteSummary` (13개 모듈, **쿠키+crumb 필요 → 브라우저에서는 대개 401**) | **스냅샷** → Yahoo `fundamentals-timeseries`(실적·밸류에이션만) → 예시 데이터 |
| 뉴스 | Yahoo `v1/finance/search` | Google News RSS → 딥링크 안내 (스냅샷에 담지 않음) |
| 원/달러 환율(시가총액 원화 환산) | Yahoo `chart/KRW=X` | **스냅샷의 환율** → 원화 환산 생략 |

스냅샷을 찾는 순서는 `SNAPSHOT_BASES` 에 있습니다 — ① 데이터 브랜치
(`raw.githubusercontent.com/.../us100-data/data/us100/`), ② 같은 폴더의 상대 경로
`data/us100/`, ③ 예전 위치인 `main`(안내 파일이 새 위치를 가리킵니다).
사내 주소로 바꾸려면 화면 ⑩ 섹션의 **데이터 경로 설정**에 넣거나 이 배열을 고칩니다.

### 데이터는 히스토리를 남기지 않는 브랜치에 둡니다

수집 결과는 `main` 이 아니라 **데이터 전용 브랜치 `us100-data`** 에 있고,
갱신할 때마다 **부모 없는 커밋 하나로 갈아끼웁니다**(과거 미보존).

    https://github.com/hanaroline/work_1/tree/us100-data/data/us100

이유는 크기입니다. 차트 100개(약 3MB)가 매일 통째로 바뀌고 가격 파일은 장중 10분마다
바뀝니다. `main` 히스토리에 쌓으면 **1년에 1GB 규모**로 붇습니다. 이 화면에서 의미가
있는 것은 지금 조회되는 값이고 과거에 조회했던 값이 아니므로, 과거를 버립니다.

| | |
|---|---|
| 올리는 절차 | `scripts/publish_us100_data.sh` — ① 브랜치의 현재 파일을 받아 깔고 ② 이번 실행이 만든 파일로 덮고 ③ `data/us100` 만 담은 부모 없는 커밋을 만들어 `--force-with-lease` 로 교체. 경쟁이 감지되면 ①부터 네 번까지 다시 |
| 두 워크플로가 같은 브랜치에 쓰는 문제 | 가격 판(10분)은 `quotes.json` 만 갱신하고 스냅샷·차트는 ①에서 받아 **보존**합니다. 반대도 같습니다 |
| `main` 에 남는 것 | `data/us100/` 에는 `{"movedTo": ...}` **안내 파일**과 REFRESH 트리거만 둡니다. 예전 HTML 을 이미 받아 둔 사람도 그 안내를 따라가 최신 값을 봅니다 |

**리셋의 대가 — 세 가지는 알고 쓰셔야 합니다.**

1. **근거 보관이 안 됩니다.** 대외 자료에 쓴 수치의 "그때 화면에 뜬 값"을 나중에 증빙해야 한다면,
   그 시점 파일을 따로 저장해 두셔야 합니다(브리핑처럼 `docs/` 에 사본을 남기는 식).
   시계열·재무 같은 값은 야후에서 다시 받을 수 있으므로 실제 손실은 이 증빙 용도뿐입니다.
2. **저장소가 즉시 작아지지는 않습니다.** force-push 로 옛 커밋은 접근 불가 객체가 되지만
   회수 시점은 GitHub 의 GC 가 정합니다(며칠~몇 주). 이미 쌓인 3MB 는 남습니다.
3. **raw 캐시가 몇 분 늦을 수 있습니다.** `raw.githubusercontent.com` 은 짧은 캐시를 두므로
   갱신 직후 몇 분간 이전 파일이 나올 수 있습니다. 화면이 **수집 시각과 나이를 그대로
   표시**하므로 오해할 일은 없지만, "10분 주기"가 때로 "13분 전"으로 보일 수 있습니다.

> 주기를 1주일 단위로 리셋하는 방식(그 사이는 히스토리 보존)도 생각했지만, 커밋마다
> 리셋하는 편이 더 낫다고 봤습니다 — "언제 마지막으로 리셋됐나"를 신경 쓸 일이 없고,
> 어차피 일주일치 과거 조회값도 쓰지 않기 때문입니다.

Actions 탭에서 수동 실행합니다. 수집은 100종목 기준 5분 안팎이 걸립니다.

> 읽어 목록을 만들기 때문에, 종목을 고치면 다음 수집부터 자동으로 반영됩니다.

> **티커가 바뀌어도 멈추지 않습니다.** 야후가 심볼을 404 로 답하면 수집기가
> `v1/finance/search` 에 회사 영문명을 넣어 현재 심볼을 찾고(미국 거래소 보통주 + 회사명 일치
> 조건), 찾은 심볼은 `sources[종목].resolvedSymbol` 에 남습니다. 화면 목록에서 그 종목이
> **조회 불가**로 표시되면 `COMPANIES` 의 심볼을 고칠 때가 된 것입니다.

> 수집기와 화면은 **같은 환산 규칙**을 씁니다(비율 → 퍼센트, 전일종가 짝 맞추기).
> 한쪽만 고치면 스냅샷과 실시간 값이 다르게 보입니다.

수집 결과는 `latest.json` 의 `summary`(`chartOk` / `summaryOk` / `crumb`)와
`sources`(종목별 단계별 성공·실패)에 남습니다. 화면 ⑩ 섹션에서도 확인할 수 있습니다.

- 각 요청은 **직접 호출 + CORS 프록시 5경로를 동시에 시도**해 가장 먼저 성공한 응답을 씁니다(각 6초 타임아웃).
- 섹션마다 응답 시각이 달라, **도착한 섹션부터 즉시 그립니다**. 느린 요청을 기다리며 빈 화면을 보여주지 않습니다.
- 100종목 지표(시가총액·PER·EPS·목표주가)는 종목별 요청이라 **화면에 보이는 행만** 채우고(기본 15개),
  나머지는 `표시 종목 지표 불러오기` 버튼으로 채웁니다(동시 5개 제한).

### 예시(데모) 데이터의 범위

사내망·CORS로 외부 요청이 전부 막히면 화면 구조를 확인할 수 있도록 **예시 값**을 표시하고,
섹션마다 `예시 데이터` 배지와 경고 문구를 띄웁니다. 예시로 만드는 것은 **시세 시계열과 지표·실적·목표주가**뿐이며,
**실적발표일·컨퍼런스콜 일정·투자의견 변경 이력·뉴스는 만들지 않습니다**(사실로 읽힐 항목을 지어내지 않기 위함).
그 항목들은 `미조회`로 남고 원문 확인 링크만 제공합니다.

### 값의 해석에서 주의한 지점

- **전일 대비 등락률** — 현재가와 전일종가를 **같은 응답에서 짝으로** 가져옵니다. 차트 메타의
  `chartPreviousClose` 는 "조회 기간 직전 종가"(1년 차트면 1년 전)라서 전일 종가로 쓰지 않습니다.
  목록의 spark 경로도 5일 창의 마지막 두 종가로 계산합니다. Stooq 폴백은 전일 종가가 없어
  **당일 시가 대비**가 되며, 그 경우 목록 아래에 안내가 붙습니다.
- **비율/퍼센트 혼용** — Yahoo 의 성장률·마진·ROE·서프라이즈는 비율(0.152 = 15.2%)로 옵니다.
  배당수익률은 응답에 따라 비율/퍼센트가 섞여, 주당배당금÷주가와 대조해 판별합니다.
- **실적발표일** — 제공사가 날짜를 두 개 주면(구간) 회사 확정 공지 전 **추정**으로 표시하고 시각은 숨깁니다.
- **컨퍼런스콜 시각** — 이 화면이 쓰는 API 에 콜 시각이 없습니다. 추정하지 않고 IR 딥링크로 안내합니다.
- **목표주가** — 개별 증권사 리포트가 아니라 Yahoo 가 집계한 컨센서스입니다(국내 증권사 의견은 빠질 수 있음).
- **증권사별 목표가는 무료 소스에 없습니다** — Yahoo 의 의견 변경 이력(`upgradeDowngradeHistory`)이 주는 것은
  일자·증권사·변경 전/후 등급·구분뿐이고 **목표가 항목이 없습니다**. 그래서 화면의 `목표가` 열은 비워 두고
  (수집기가 `pt` 로 받을 자리를 만들어 두었으니 제공사가 넣어 주면 그대로 채워집니다), 대신 우리가 가진
  일봉에서 **그 의견이 나온 날의 종가**와 **지금까지의 등락**을 계산해 함께 보여 줍니다. 증권사별 목표가가
  꼭 필요하면 유료·키 발급이 필요한 소스(Finnhub·FMP·Benzinga 등)를 붙여야 하고, 그 키는 저장소가 아니라
  Actions 시크릿에 두어야 합니다.
- **기업 개요의 한글 요약** — 주력사업·개요·사업 키워드(100개 기업)는 공개된 사업 구조를 화면에 정리해 둔
  상수이고, 영문 원문 개요는 제공사의 기업 프로필(`assetProfile.longBusinessSummary`)입니다. 출처가 다르므로
  화면에서도 구분해 적습니다.
- **보조지표** — 볼린저밴드(20, ±2σ)·MACD(12,26,9)·RSI(14)는 정의 그대로 브라우저에서 계산합니다(라이브러리 없음).
  MACD 는 느린 EMA 가 자리 잡기 전 구간을, RSI 는 첫 14봉을 비워 둡니다. 봉이 모자라면 그리지 않고 이유를 적습니다.
- **비교 종목 수를 4개로 둔 이유** — 승인된 시리즈 색이 4색(오렌지·남색·연오렌지·하늘)이고,
  5개 이상이면 뒤 색이 앞 색과 구분되지 않으며 기간별 수익률 막대의 값 라벨이 겹쳐 못 씁니다.
  그래서 종목 수를 늘리는 대신 **조합을 저장해 갈아 끼우는** 쪽으로 풀었습니다.
- **비교 차트의 리베이스** — 고른 기간의 **첫 종가를 100** 으로 맞춥니다. 마지막 점은 지금 가격(스트리밍·가격
  파일·스냅샷 중 가장 신선한 것)으로 맞추고, 배당 재투자는 반영하지 않습니다. 기간별 수익률 비교는 차트 기간과
  무관하게 받아 둔 전체 시계열(월봉 10년 + 일봉 2년)로 계산합니다.

## 대상 100개 기업

`us-top100.html` 안 `COMPANIES` 배열에 `[Yahoo 심볼, 영문명, 한글명, 섹터코드]` 로 들어 있습니다.
종목을 바꾸려면 이 배열만 고치면 됩니다(검색 키워드는 `KEYWORDS`).

> **목록은 고정입니다.** 지수가 아니고, `#` 열의 순서는 순위가 아니며, 시가총액이 바뀌어도
> 자동으로 갱신되지 않습니다. 실제 순위는 정렬을 **시가총액**으로 두면 조회한 값으로 매겨집니다.

### 대상 목록은 매주 자동 교체, 점검은 매일

목록은 **매주 월요일 아침(08:00 KST)** 자동으로 갈아 끼웁니다. 오래 손대지 않았던 이유는 화면의
**한글 자산**(기업명·검색 키워드·"기업 한눈에" 개요)이 종목마다 사람이 쓴 것이어서, 기계적인 교체가
*한글이 빈 종목이 조용히 섞여 들어오는* 방식이 되기 때문이었습니다. 그래서 **한글을 쓰는 일까지 포함해**
자동화했습니다 — 주간 작업이 Claude 세션으로 돌면서 새 종목의 한글명과 개요(주력사업·서술·키워드)를
다른 99개와 같은 말투·깊이로 써서 넣습니다.

교체는 `scripts/us100_list_tool.py` 를 통해서만 일어나고, 그 도구가 안전장치를 강제합니다.

| 안전장치 | 값 | 왜 |
|---|---|---|
| 편입 자격 | 지금 시총 **100위 안** | 경계에서 오가는 종목을 넣었다 뺐다 하지 않는다 |
| 제외 자격 | **130위 밖**으로 밀린 종목 | 위와 같은 이유, 방향만 반대 |
| 한 번에 | **최대 3종목** | 주마다 화면이 낯설어지지 않게 |
| 보호 종목 | `TSM`·`ASML` | 순위와 무관하게 담아 달라고 한 종목 |
| 개수 | 편입 수 = 제외 수, 결과는 언제나 **100개** | |
| 시세 확인 | 넣기 전에 **한 달 일봉이 실제로 나오는지 확인** — 확인은 매일 점검(러너)이 해서 `ranking.json` 에 `tradable` 로 적어 둔다 | 비상장 평가액이 순위에 섞여 들어오면(예: `SPCX` 가 7위) 그 종목만 "미조회"로 남는다. 주간 작업이 도는 자리는 야후로 나가지 못해(망 정책), 나갈 수 있는 러너가 대신 확인한다 |
| 한글 | 한글명 없으면 거부, 개요가 60자 미만이면 거부 | 빈칸이 섞이지 않게 |
| 문법 | 고친 뒤 `node --check` 까지 통과해야 저장 | 통과 못 하면 **아무것도 쓰지 않는다** |

종목 하나를 바꾸려면 `COMPANIES`·`PROFILE_KO`·`KEYWORDS`·`FOREIGN` 네 곳을 함께 고쳐야 하는데,
한 곳이라도 빠지면 그 종목만 이름이 비거나 "기업 한눈에"가 빈 채로 나옵니다. 도구가 네 곳을 함께 고치고
마지막에 검사합니다. 교체가 일어나면 `var BUILD` 도 함께 올라가, 이미 파일을 받아 둔 사람이 새 파일을
열 때 처음 상태로 시작합니다.

```bash
python scripts/us100_list_tool.py report          # 후보와 안전장치 통과 여부
python scripts/us100_list_tool.py apply --plan plan.json
python scripts/us100_list_tool.py validate        # 고치지 않고 검사만
```

교체 뒤에는 `data/us100/REFRESH` 를 건드려 push 하므로 전체 수집이 곧바로 한 번 더 돌고,
새 종목의 지표·실적·뉴스·차트가 그날 안에 채워집니다(세션 토큰으로는 `workflow_dispatch` 가
403 이라 push 로 부릅니다).

수집 주기는 그대로입니다 — **전체 수집은 매일**, 가격은 장중 30분 주기.

점검은 매일 돕니다. 매일 수집 때 `scripts/check_us100_ranking.py` 가 **지금 시가총액 상위 100** 과 목록을 견주어
차이만 보고합니다.

- 순위 경로 ① 야후 스크리너(`POST /v1/finance/screener`, crumb 필요, 시총 내림차순 상위 260)
  ② 막히면 S&P 500 구성종목 + `v7/finance/quote` 일괄 조회. 우리 목록의 시총은 방금 수집한
  `latest.json` 값을 씁니다(요청을 아끼고 같은 판의 값으로 순위를 매깁니다).
- **추가 후보**: 상위 100인데 목록에 없는 종목 — 미국에 상장한 외국 기업(ADR)일 수 있어 `assetProfile.country`
  를 함께 적습니다(예: `TSM … 본사 Taiwan(미국 상장 외국 기업)`).
- **밀린 종목**: 목록에 있으나 **120위 밖**으로 내려간 종목(경계에서 오가는 잡음을 걸러내기 위한 여유).
- 점검은 **전체 수집과 따로 도는 가벼운 워크플로**입니다(`.github/workflows/us100-ranking.yml`,
  매일 22:00 UTC · 1~2분). 필요한 것이 데이터 브랜치의 `latest.json` 뿐이라 8분 걸리는
  전체 수집에 매달아 둘 이유가 없고, 수집이 느린 날에 점검까지 못 도는 일도 피합니다.
  지금 돌리려면 `data/us100/RANK_REFRESH` 를 한 줄 고쳐 push 하면 됩니다.
- 결과는 세 곳에 남습니다 — `data/us100/ranking.json`(데이터 브랜치), **Actions 실행 요약**,
  그리고 **이슈 하나**(`대상 목록 갱신 후보 (미국 100대 기업)`, 매일 같은 글을 갱신).
- 화면은 ⑩ 섹션에 그 결과를 그대로 보여 줍니다 — 후보가 없으면 `목록이 지금 상위 100과 일치합니다`,
  있으면 종목·시총·현재 순위를 적습니다.

손으로 고칠 때도 같은 도구를 쓰는 편이 안전합니다(네 곳을 함께 고치고 검사까지 합니다).
미국에 상장했지만 본사가 미국이 아닌 기업은 `FOREIGN` 에 넣어 화면에 **해외** 표시와 본사 국가가
함께 나오게 합니다 — 2026-09-08 기준 TSMC(대만)·ASML(네덜란드) 두 곳이 그렇게 담겨 있고,
대신 순위가 가장 낮았던 FISV·NKE 를 뺐습니다. 이 둘은 주간 자동 교체에서 **보호 종목**이라 빠지지 않습니다.

## 두 가지 판 — 어느 것을 쓰나

| | **실시간 판** | **오프라인 판** |

> 오프라인 판이 따로 필요한 이유: `file://` 로 열린 페이지는 **옆에 있는 json 파일조차**
> 브라우저가 CORS 로 막습니다(origin `null`). 그래서 데이터를 HTML 안에 넣어 두는 수밖에
> 없습니다. 오프라인 판은 배지에 `내장 스냅샷 09.09 12:44` 처럼 **만든 시점을 밝히므로**,
> 오래된 파일을 실시간 시세로 착각할 일은 없습니다.
>

## 대상 종목은 매주 저절로 바뀝니다

| 규칙 | 값 | 왜 |
|---|---|---|
| 들어오는 조건 | 시총 **90위 안** | |
| 나가는 조건 | 시총 **110위 밖** | 사이의 완충 구간이 100위 언저리에서 매주 오가는 종목을 걸러 줍니다 |

**새 종목의 한글 자산은 지어서 함께 넣습니다.** 예전에는 이것이 사람 손이어서 자동 교체를
하지 않았습니다 — 검색 키워드와 "기업 한눈에" 개요가 없으면 그 종목만 화면이 반쯤 비기

| 무엇 | 어디서 |
|---|---|
| 한글 사명 | **상장공시시스템(KIND) 상장법인 목록** → 없으면 야후에 한국어(ko-KR)로 질의 → 그래도 없으면 영문명 그대로 |

| 기업 개요 | 수집한 사실만으로 짓습니다 — 상장 시장·업종·주요제품·최근 12개월 매출·영업이익률·시총 순위·임직원 수 |

**셋 중 하나라도 만들지 못하면 그 종목은 넣지 않습니다**(시세를 못 받거나 기업 프로필이
비었을 때). 다음 주 점검에서 다시 봅니다. 목록을 고친 뒤 재수집에서 새 종목의 시세가
안 오면 커밋하지 않고 화면 파일을 되돌립니다.

자동으로 지은 개요는 **사람이 쓴 글이 아니라는 것을 화면이 밝힙니다** — `PROFILE_KO` 항목의
네 번째 자리에 `'auto'` 가 붙고, "기업 한눈에" 아래 출처 문구가 그 사실을 적습니다. 나중에
문장을 사람이 고치면 그 `'auto'` 표시만 지우면 됩니다. 화면 ⑩ 섹션에는 지난 주간 갱신에서
무엇이 바뀌었는지 한 줄로 나옵니다(`list-change.json`).

손으로 바꾸고 싶을 때도 그대로 됩니다 — `COMPANIES`·`KEYWORDS`·`PROFILE_KO` 를 함께 고친 뒤
`python scripts/update_kr100_list.py --check` 로 셋이 어긋나지 않는지 확인하세요. 어떤 종목이
들어오면 무엇이 적힐지 미리 보려면 `--probe 052690,039030` 을 쓰면 됩니다(목록은 건드리지
않습니다).

순위 원천이 응답하지 않으면 목록 점검은 `ranking.json` 을 **쓰지 않고** 경고만 남깁니다.
반쯤 맞는 순위를 올리면 화면 ⑩ 섹션이 "목록이 상위 100과 일치합니다" 라고 잘못 말하게 되기
때문입니다(그 경우 화면은 목록 점검 안내를 아예 감춥니다).

> **한국거래소(data.krx.co.kr)는 쓰지 않습니다.** 전종목 시세를 주는 `getJsonData` 가
> GitHub 러너에서 **HTTP 400 + 본문 `LOGOUT`** 을 돌려줍니다. Referer·쿠키·`bld` 를 바꿔
> 네 가지로 시도해도 같았습니다(2026-09-09 러너에서 확인). 거래소가 클라우드 IP 를 거부하는
> 형태여서 헤더로 풀리는 문제가 아니라, 야후 스크리너로 갈아탔습니다. 사내망처럼 국내 IP 가
> 나가는 환경에서는 KRX 가 열릴 수 있으니, 더 정확한 순위가 필요하면 그쪽에서 받는 편이 낫습니다.
>
> 스크리너 결과에서는 **우선주**(종목코드 끝자리가 0 이 아닌 것 — 야후가 삼성전자 우선주에
> 보통주 기준 시가총액을 붙여 3위로 올려 보냅니다)와 **스팩·리츠**를 걸러냅니다.
>
> **상장공시시스템(KIND)의 상장법인 목록도 러너에서는 막혀 있습니다** — `corpList.do` 가

> 갱신이 먼저 찾아보지만, 예약 실행에서는 한글 사명을 야후(`lang=ko-KR`)에서 받고 키워드는
> 영문 개요에서 뽑은 말로 채웁니다. 국내 IP 에서 손으로 돌리면 KIND 가 열려 더 나은 이름과

날짜 표시만 새로 그립니다. 오늘에 머물러 있었을 때만 새 오늘로 따라 옮깁니다.

### 시각 기준 — 한국 시각이 기본입니다

빌더는 일정마다 **발표기관 현지 날짜**와 **한국 시각 환산**을 함께 담습니다. 둘은 날짜가
어긋날 수 있습니다 — FOMC 는 뉴욕 시각 9/16 오후 2시에 결정하지만 한국에서는 **9/17 새벽
3시**입니다. 처음에는 날짜 칸에 현지 날짜를, 시각 칸에 한국 시각을 함께 보여 주었는데 한
줄 안에서 기준이 갈려 읽기 어려웠습니다.

지금은 상단 툴바의 **시각 기준** 단추로 하나를 고르고, **달력 배치·D-day·목록 정렬·기간
필터까지 모두** 그 기준을 따릅니다. 기본은 한국 시각이라 위 FOMC 는 **9/17 칸**에 놓입니다.
발표 시각이 공표되지 않은 일정은 옮길 근거가 없어 현지 날짜 그대로 둡니다. CSV 로 내려받으면
`date_shown` · `date_local` · `time_local` · `tz` · `time_kst` 를 모두 담아 줍니다.

## 날짜를 지어내지 않습니다 — 확정도 다섯 단계

일정은 "언제 발표되는가"가 전부인 자료라, 틀린 날짜 하나가 자료 전체의 신뢰를 깎습니다.
그래서 모든 일정에 **어디까지 확인된 날짜인지**를 붙여 화면에 배지로 그립니다.

| 배지 | 뜻 | 어디서 오나 |
|------|-----|-------------|
| **확정** | 발표기관의 공식 일정에서 확인 | 러너(`scripts/fetch_calendar.py`)가 원문 페이지에서 받은 값. 휴장일은 `data/market/holidays.json` |
| **교차확인** | 검색으로 교차 확인 — 공식 페이지 재확인 전 | 세션에서 넣은 seed 값. 러너가 한 번 돌면 확정으로 올라갑니다 |
| **잠정** | 기관이 스스로 "잠정"으로 공표 | FOMC 익년 일정처럼 기관이 tentative 라고 적어 둔 것 |
| **추정구간** | 데이터 제공사의 추정 구간 | 실적발표일이 두 날짜(구간)로 오면 회사 확정 공지 전이라는 뜻입니다. 시각은 숨깁니다 |
| **규칙추정** | 발표 주기 규칙으로 만든 날짜 — **확정 아님** | "미국 CPI 는 통상 매월 둘째 주" 같은 규칙. ① 카드에 올리지 않고, ICS 에서는 제목에 `(추정)` 을 붙여 `STATUS:TENTATIVE` 로 내보냅니다 |

**확인하지 못한 일정은 캘린더에 넣지 않습니다.** 개최 시기만 알려진 학회 26곳, MSCI·KRX
지수 정기변경, 배당기준일, 국고채 입찰, 공모주·락업은 날짜를 만들지 않고 ⑦·⑧ 아래에
이름과 공식 링크만 둡니다. 확인 못 한 자리(한국은행 2027년 일정 등)는 ⑩에 그대로 적힙니다.

**발표 시각도 만들지 않습니다.** 일본은행과 금통위는 발표 시각이 공표돼 있지 않아
`시각 미공표` 로 둡니다. 컨퍼런스콜 시각은 이 화면이 쓰는 소스에 없어 IR 링크로 넘깁니다.

## 두 가지 판 — 어느 것을 쓰나

| | `market-calendar.html` (인터넷판) | `market-calendar-offline.html` (오프라인판) |
|---|---|---|
| 데이터 | 열 때마다 `latest.json` 을 **받아온다** | 파일 안에 **심겨 있다** |
| 갱신 | 주 1회 수집이 돌면 **다시 열기만 하면 최신** | 주 1회 수집이 **새 판을 아래 고정 주소에 올려 둔다** — 받아서 다시 옮겨야 바뀐다 |
| 필요한 것 | 저장소 옆자리 또는 `raw.githubusercontent.com` 접근 | **아무것도 필요 없음** |
| 크기 | 약 0.2MB | 약 0.5MB |
| 표시 | — | ⑩ 상단에 `오프라인 판` 배지 |

**인터넷판**은 데이터를 두 곳에서 앞에서부터 찾습니다 — ① 저장소 옆자리(로컬 서버로 열었을
때) ② `main` 브랜치. 그래서 로컬 서버로 열어도, 파일 하나만 옮겨 `file://` 로 열어도
(그 PC 에 인터넷이 있으면) 동작합니다.

```bash
# 저장소를 통째로 두고 보는 경우
python3 -m http.server 8000
# 브라우저에서 http://localhost:8000/market-calendar.html
```

**오프라인판**은 인터넷이 아예 안 되는 업무용 PC 용입니다. `file://` 로 열린 페이지는 옆에
있는 JSON 도 브라우저 보안정책에 막혀 못 읽으므로, 데이터를 HTML 안에 심어 둡니다.

```bash
python scripts/inline_calendar.py       # market-calendar-offline.html
```

### 오프라인판 받는 자리 — 매주 이 주소가 새 판으로 바뀝니다

오프라인판은 **스스로 갱신될 수 없습니다.** 데이터를 파일 안에 품고 있으니 당연합니다.
대신 주 1회 수집이 새 판을 만들어 **늘 같은 주소**에 올려 둡니다. 받아서 업무용 PC 로
다시 옮기면 그 주 일정이 반영됩니다.

```
https://raw.githubusercontent.com/hanaroline/work_1/calendar-data/data/calendar/market-calendar-offline.html
```

> 브라우저로 열면 소스가 그대로 보입니다 — **다른 이름으로 저장**(Ctrl+S) 하거나
> `curl -o market-calendar-offline.html <위 주소>` 로 받으십시오.

`calendar-data` 는 **히스토리를 남기지 않는 데이터 전용 브랜치**입니다(`kr100-data` ·
`us100-data` 와 같은 방식). 매주 500KB 가 통째로 바뀌는 파일이라 `main` 히스토리에 쌓으면
1년에 26MB 가 붇는데, 지난주 판을 되짚을 일은 없기 때문입니다. 갱신할 때마다 부모 없는
커밋 하나로 갈아끼웁니다.

수집 워크플로의 **Artifacts**(`calendar-data`, 14일 보관)에도 그대로 남고, 위 명령으로
직접 만들어도 같은 파일입니다. `main` 에는 커밋하지 않습니다.

## 데이터 구조

```
data/calendar/
  latest.json              화면이 읽는 단 하나의 파일 (약 276KB)
  fetch-report.json        러너의 수집 결과 — 경로별 성공/실패와 seed 와의 차이
  REFRESH                  한 줄 고쳐 push 하면 수집 워크플로가 돈다
  seed/
    centralbanks.json      Fed·한국은행·ECB·BOJ·BOE·PBOC 정책결정일
    indicators.json        지표 23개의 정의·발표기관·공표일정 링크·확인된 발표일·발표 주기 규칙
    conferences.json       제약·바이오 학회 9곳(날짜 확인) + 21곳(시기만) + 산업 콘퍼런스 6곳
    market-events.json     만기·리밸런싱 규칙 6개 + 지수 정기변경 3곳 + 원문으로 볼 일정 7개
```

`seed/` 는 **사람이 확인해 넣는 자리**이고, 항목마다 `url` · `source` · `verified_at` 을
적습니다. 휴장일을 `holidays.json` 에 둔 것과 같은 이유입니다 — 날짜를 빌더 코드에
문자열로 박아 두면 틀린 채로 굴러다닙니다.

빌더(`scripts/build_calendar.py`)가 seed 와 **이미 있는 파일들**을 합쳐 `latest.json` 을
만듭니다. 같은 값을 두 곳에서 따로 모으지 않습니다.

| 재사용하는 것 | 어디서 | 무엇에 |
|---|---|---|
| 6개 시장 휴장일·조기마감 | `data/market/holidays.json` | ② 격자 음영, ⑧ 휴장일 표, **만기일 보정** |
| 국내·미국 200개 기업 실적발표일 | `data/{kr100,us100}/latest.json` | ⑥ 실적·컨콜 |
| 종목명 200개 | `kr-top100.html` · `us-top100.html` 의 `COMPANIES` | ⑥ 에서 티커에 이름 붙이기 |
| 정책금리·연방기금선물 내재금리 | `data/market/latest.json` | ⑤ 통화정책 맥락 |

빌더가 계산하는 것: **KST 환산**(브라우저에 시간대 데이터를 두지 않기 위해),
**만기일 휴장 보정**(겹치면 앞 영업일로 당김. 중국 LPR 은 뒤로 밈), FOMC 일정에서
파생되는 **의사록 공개일**(3주 뒤) · **베이지북**(2주 전 수요일) · **블랙아웃 기간**
(회의 시작 두 번째 앞 토요일 ~ 회의 다음 목요일 — 연준이 정한 규칙 그대로).

규칙으로 날짜를 만드는 창은 두 가지입니다 — 매달 오는 것은 **180일치**, 분기·연 1회로
드물게 오는 것은 **400일치**. 3월에만 있는 주주총회 시한이 180일 창에 한 번도 안 들어와
0건이던 것을 고친 결과입니다.

## 데이터 수집 (주 1회 자동)

`.github/workflows/calendar-data.yml` — **매주 월요일 오전 10시 KST**(`cron: '0 1 * * 1'`
— 월 01:00 UTC). 캘린더는 매일 바뀌는 자료가 아니어서 주 1회로 잡았고, 한 주가 시작될 때
그 주 일정이 갱신돼 있도록 월요일 오전에 둡니다. 지금 돌리려면 `data/calendar/REFRESH` 를
한 줄 고쳐 push 하십시오.

> cron 은 **UTC 로만** 읽힙니다(타임존을 지정할 수 없습니다). KST 는 UTC+9 이고 서머타임이
> 없으므로 9시간을 빼면 됩니다 — 월요일 10:00 − 9h = 같은 월요일 01:00.
>
> GitHub 의 예약 실행은 **정시를 보장하지 않습니다.** 특히 매시 정각은 요청이 몰려 몇 분에서
> 십수 분 늦게 뜨는 일이 흔합니다. 분 단위로 급한 수집이 아니라 그대로 두었습니다.

한 번 돌 때 하는 일은 넷입니다.

| | 하는 일 | 어디에 남나 |
|---|---|---|
| 1 | 파서를 모의 응답으로 먼저 검사 | 실패하면 수집을 시작하지 않습니다 |
| 2 | 발표기관 원문에서 확정 날짜를 받아 seed 를 `official` 로 올림 | `data/calendar/seed/**` · `fetch-report.json` |
| 3 | `latest.json` 을 다시 만들고 검사 | `main` — **인터넷판은 다시 열기만 하면 최신** |
| 4 | 오프라인판을 새 화면·새 데이터로 다시 만들어 올림 | `calendar-data` 브랜치의 고정 주소 |

> **오프라인판은 화면을 고친 날에도 다시 만듭니다.** `market-calendar.html` 이나
> `scripts/inline_calendar.py` 를 push 하면 워크플로가 바로 돕니다. 그러지 않으면 다음
> 월요일까지 배포 자리에만 옛 화면이 남습니다.
>
> 4번은 `main` 에서 돌 때만 합니다 — 사람이 받아 가는 자리라 작업 브랜치의 중간 판이
> 덮어쓰면 안 되기 때문입니다. 작업 브랜치에서 돌린 결과는 Artifacts 로 확인합니다.

수집이 한 곳이라도 실패하면 실행 요약에 `::warning::` 으로 적히고 어느 경로가 왜 비었는지
표로 남습니다. 예약 실행이 통째로 실패하면 GitHub 은 **cron 을 마지막으로 고친 사람**에게
메일을 보냅니다(저장소 전체가 아닙니다). **실패해도 seed 는 덮어쓰지 않습니다** — 건수·날짜
범위·연간 회의 횟수를 견주어 의심스러우면 그대로 둡니다.

> 예약 실행은 **저장소가 60일 동안 조용하면 GitHub 이 자동으로 끕니다.** 이 저장소는 다른
> 수집이 매일 돌아 해당되지 않지만, 오래 손대지 않을 때는 Actions 탭에 `이 워크플로가
> 비활성화되었습니다` 배너가 뜨는지 한 번 보십시오.

### 러너에서 실제로 돌려 본 결과 (2026-09-10)

첫 실행에서 다섯 곳이 **HTTP 200 을 받고도 0건**을 뱉었습니다. 검사가 제 몫을 해 seed 는
지켜졌지만, 세션에서는 그 사이트에 붙지 못해 무엇이 어긋났는지 알 수 없었습니다. 그래서
파서가 걸러졌을 때 **받은 페이지의 구조를 로그와 `fetch-report.json` 에 남기는 진단**을
넣고 다시 돌렸고, 원인이 셋으로 갈렸습니다.

**구조 가정이 틀렸던 것** — 파서를 고쳐 해결했습니다.

- **FOMC** — 페이지에 `2026 FOMC Meetings` 헤딩과 `January 27-28` 이 그대로 있는데,
  `<h4>` 바로 뒤에 연도가 오리라 본 정규식이 빗나갔습니다. 헤딩 안에 태그가 하나 더 있습니다.
- **BOE · BOJ** — 날짜에 연도가 붙어 있지 않습니다. 연도는 구획 헤딩
  (`2026 confirmed dates` · `<h2>2026</h2>`)에 있습니다.

지금은 클래스 이름과 태그 구조에 기대지 않습니다. **연도 표시를 기준으로 원본을 구획으로
자르고, 그 구획의 본문에서 `월 일자` 를 읽습니다.** 기관이 페이지를 다시 만들어도 '연도'
라는 글자와 '월 일자' 표기는 남습니다.

**이 주소로는 안 되는 것** — 다른 길이 필요합니다.

- **ECB · 한국은행** — 본문에 날짜가 **아예 없습니다**. 자바스크립트로 그리는 판입니다.
  정적으로 내려오는 다른 주소를 후보로 붙여 두었고, 그래도 안 되면 seed 의 `교차확인`
  날짜가 그대로 남습니다(⑩에 그 사실이 적힙니다).
- **BLS** — 세 경로 모두 **403** 입니다. 러너 IP 차단으로 보이며 페이지를 아예 못 받으니
  파서로는 풀리지 않습니다. 같은 통계를 FRED 가 API 로 주므로 CPI(release 10)·
  고용상황(50)을 FRED 쪽에 더해 두었습니다 — **무료 키를 넣으면 그 길로 채워집니다.**

### 파서가 느슨한 만큼 안전장치를 하나 더 답니다

연도 구획 안의 `월 일자` 를 그러모으는 방식이라, 엉뚱한 표를 읽으면 **날짜 형식은 멀쩡한데
개수가 먼저 어긋납니다**. 그래서 중앙은행마다 연간 회의 횟수(`meetings_per_year`)를 seed 에
적어 두고, 온전히 담긴 해의 개수가 그 범위를 벗어나면 반영하지 않습니다. 연 8회 기관에
30건이 들어오면 걸러지고 8건은 통과하는 것을 점검에 넣었습니다.

### 의심스러우면 덮어쓰지 않습니다

HTML 을 긁는 경로는 상대가 페이지 구조를 바꾸면 조용히 빈 값을 뱉습니다. 그때 seed 를
덮어쓰면 검색으로 확인해 둔 날짜까지 사라집니다. 그래서 파서마다 **최소 건수와 날짜 범위**를
검사해 통과할 때만 반영하고, 실패는 `fetch-report.json` 과 Actions 실행 요약에 남깁니다.
받은 날짜가 seed 와 다르면 **그 차이도 함께 적습니다** — 조용히 바뀌면 왜 달라졌는지
알 수 없기 때문입니다. 한 경로가 막혀도 나머지 수집은 계속 갑니다.

```bash
python scripts/fetch_calendar.py --dry-run        # 받아서 견주기만, 파일은 안 고침
python scripts/fetch_calendar.py --only fomc,boe  # 일부 경로만
python scripts/fetch_calendar.py --try-blocked    # 못 받는다고 적어 둔 곳도 다시 시험
```

### FRED API 키 넣기 (미국 CPI·고용상황 확정 발표일)

BLS 가 러너 IP 에 403 을 주므로, 미국 CPI·고용상황·PCE·GDP·소매판매의 **확정** 발표일은
지금 FRED 경로로만 들어옵니다. 무료 키 하나면 켜집니다.

1. <https://fredaccount.stlouisfed.org/apikey> 에서 계정을 만들고 **API key** 를 발급합니다
   (무료, 승인 대기 없음. 32자리 문자열입니다).
2. 저장소 **Settings → Secrets and variables → Actions → New repository secret** 으로 갑니다.
3. 이름을 정확히 `FRED_API_KEY` 로 하고 값에 그 키를 붙여 넣습니다.
4. `data/calendar/REFRESH` 를 한 줄 고쳐 push 하면 바로 수집이 돕니다.

키를 넣었는지는 Actions 실행 요약의 `fred:*` 줄로 확인합니다 — 없으면
`FRED_API_KEY 가 없어 건너뛰었다`, 있으면 지표별 건수가 찍힙니다.
키는 시크릿에만 두고 저장소 파일에는 넣지 마십시오.

- **모멘텀** — *추세가 아래로 꺾였는가.* MACD 히스토그램, RSI, 20일 이격도, 20일선 기울기,

두지 않으면 합산에서 뒤섞입니다.

## 점수를 어떻게 만드는가

**고정 문턱을 쓰지 않습니다.** 「RSI 30 이하면 과매도」 같은 자리는 지수 수준도 변동성 수준도
해마다 달라져, 2024년에 위태롭던 값이 2026년에는 예사인 일이 생깁니다. 대신 각 지표가
**제 과거 1년 안에서 몇 번째인지**(백분위)로 옮겨 씁니다. 눈금이 옮겨져도 뜻이 흔들리지
않습니다. 표본이 60일에 못 미치면 값을 내지 않습니다 — **0 이 아니라 없음입니다.**

**가중치는 자료가 정하되, 모르는 것은 사전값으로 돌립니다(워크포워드 + 축소).** 축마다
「그 축의 점수가 높던 날 뒤에 실제로 더 많이 밀렸는가」의 순위상관 ρ 를 **그때까지의 과거만으로**
재고(t 일의 가중치는 결과가 이미 드러난 j+10 < t 인 날만 씁니다), 한 달에 한 번 다시 잽니다.
그리고 그 잰 값을 **증거의 힘 λ 만큼만** 믿습니다.

```
최종 가중치 = λ × 잰 몫 + (1 − λ) × 사전값(균등 25%)      ← 뒤에 다시 정규화
λ = 유효표본 / (유효표본 + 10)
유효표본 = 관측 수 ÷ 10                                   ← 중첩 보정
```

**중첩을 보정하는 까닭.** 오늘의 「이후 10거래일 낙폭」과 내일의 그것은 아흐레를 공유합니다.
관측 400개가 독립 400개가 아니라 마흔 개어치입니다. 이것을 무시하면 표준오차가 √10 배 작게
나와 우연히 생긴 상관을 실력으로 읽습니다.

이 저장소 자료에서 지금 나오는 값입니다.

| 축 | ρ | 표본 | 유효표본 | λ(증거) | 잰 몫 | 사전값 | **최종 가중치** |
|---|---|---|---|---|---|---|---|
| 변동성 | +0.285 | 391 | 39.1 | 0.80 | 79% | 25% | **57%** |
| 자금수급 | 잴 수 없음 | 10 | — | 0.00 | — | 25% | **21%** |
| 모멘텀 | +0.074 | 446 | 44.6 | 0.82 | 21% | 25% | **18%** |
| 가격압축 | −0.105 | 454 | 45.4 | 0.82 | 0% | 25% | **4%** |

### 왜 문턱을 없애고 이렇게 바꿨는가

처음에는 「관측 60개가 안 되면 그 축은 점수에서 뺀다」로 두었습니다. 그랬더니 **자금수급 축이
통째로 빠졌습니다.** 그 축이 88점을 가리키는데도 점수에는 없으니, 화면을 급히 보는 사람은
낮은 점수를 보고 안전하다고 읽습니다. 수급 전환을 미리 잡자고 만든 도구에서 이건 그냥 흠이
아니라 도구의 목적을 무너뜨리는 흠입니다.

그렇다고 **문턱만 낮추는 것으로는 풀리지 않습니다.** 수급의 상관은 관측 19개에 ρ=−0.21,
표준오차 0.25 로 **잰 것이 없는 것과 같습니다.** 문턱을 낮추면 `max(0, ρ)` 가 0 이 되어
가중치 0 으로 들어가고, 결국 빠진 것과 똑같아집니다.

그래서 문턱을 아예 없앴습니다. 증거가 두터운 축은 잰 값 쪽으로, 얕은 축은 사전값 쪽으로
갑니다. 이러면 **값이 있는 축은 언제나 점수에 들어가고**, 자료가 쌓이는 만큼 저절로 잰 값이
사전값을 밀어냅니다 — 넘어야 할 턱이 없습니다.

지금 수급 축은 **21% 가중치로 점수에 들어가 있고**, 그 덕에 오늘 점수가 50점에서 58점으로
올라갑니다. 다만 그 21% 는 **사전값에서 온 것이지 과거 실적으로 확인된 것이 아닙니다.**
화면은 축마다 「과거 실적으로 잰 값」과 「거의 사전값 — 실력 확인 안 됨」을 딱지로 갈라 붙이고,
수급처럼 실력이 확인되지 않은 축이 70점을 넘으면 맨 위에 따로 칸을 세웁니다. 재검산이
이 딱지와 칸을 강제합니다 — 지우면 나가는 값이 1 입니다.

### 수급이 든 판과 안 든 판을 섞어 견주는 문제

수급 원자료는 52일치인데, 누적(20일)과 z점수 창이 앞자락을 먹어 **점수에 실제로 들어간 날은
34일**입니다. 이력은 484일이므로 **문턱과 백분위를 재는 이력의 대부분은 수급이 빠진 판**입니다.
오늘 점수를 그 이력과 견줄 때는 그만큼 감안해야 하고, 화면 맨 위와 `notes` 의 「수급반영」 칸이
이 사실을 수급을 넣기 전 점수와 함께 적어 내보냅니다.

같은 까닭으로 **아래 백테스트 성적은 사실상 가격 세 축의 성적입니다** — 평가 구간 274일 가운데
수급이 든 날이 34일뿐이라, 수급이 든 채로 겪은 급락 사건이 아직 표본이 못 됩니다. 수급을 넣은
뒤 리프트가 +10.4%p 에서 +9.9%p 로 움직인 것도 실력 차이가 아니라 그 34일이 만든 잡음입니다.

**등급은 점수의 자기 백분위로 붙입니다.** 「65점」은 셈법을 바꾸면 뜻이 달라지지만
「제 이력의 상위 5%」는 바뀌지 않습니다. 고객에게 옮길 때도 이쪽이 옳습니다 — 「경계」가
「이만한 자리는 두 해에 스무 날쯤 나옵니다」로 풀리기 때문입니다.

## 시나리오 확률 — 지어낸 것이 아니라 센 것

오늘과 **같은 국면**(압축 대기 · 하락 전개 · 변동성 확산 · 완만 상승 · 안정)이던 과거 날들을
모아, 그 뒤 5·10·20거래일에 실제로 무슨 일이 있었는지를 셉니다. 급락·약세·횡보·상승의
경계는 **고정 퍼센트가 아니라 그날 변동성의 σ 배**입니다 — 연 44% 로 흔들리는 장에서 ±3% 는
아무 일도 아니고, 잠잠한 장에서는 큰 사건이기 때문입니다. 화면에는 오늘 변동성으로 환산한
퍼센트를 함께 적습니다(예: 「10거래일 안에 −12.4% 이하」).

**같은 국면이 20일도 안 되면 확률을 내지 않고 「표본 부족」이라고 적습니다.** 열 개 중 셋이
급락이었다고 30% 라 적는 것이 이 일에서 가장 흔한 거짓말입니다. 확률을 낼 때는 **표본 수와
무조건부 확률을 반드시 옆에 같이** 싣습니다 — 급락 확률 5% 는 그 자체로 아무 말도 아니고,
평소가 13% 였다는 것과 나란히 놓아야 뜻이 생깁니다.

## 백테스트 — 이 경보는 쓸 만한가

두 가지 잣대로 각각 잽니다. **절대 낙폭**은 고객이 실제로 겪는 것이고, **σ 기준**은
「변동성이 높아졌다」는 몫을 빼고도 실력이 남는지를 묻는 더 엄한 시험입니다. **두 답이 다르므로
둘 다 싣습니다.**

다섯 줄 모두 **같은 구간·같은 경보 빈도(상위 20%)** 로 재야 견줄 수 있습니다. 처음에 이것을
하지 않았더니 늦게 시작하는 계열일수록 겪은 사건이 적어 포착률이 저절로 높아졌습니다 —
적응 가중이 4건에 100%, 변동성 단독이 9건에 89% 로 찍혀 앞의 것이 나아 보였는데, 같은
구간에서 다시 재니 순서가 뒤집혔습니다.

**절대 낙폭 기준** (10거래일 안에 10% 이상 하락 · 2025-08-01~2026-09-16 · 274세션 · 급락 8건)

| 점수 | 경보일 | 포착 | 포착률 | 정밀도 | 기준선 | 리프트 |
|---|---|---|---|---|---|---|
| **적응 가중** | 113일(41%) | 8/8 | **100%** | 29.2% | 19.3% | **+9.9%p** |
| 균등 가중 | 86일(31%) | 5/8 | 63% | 23.3% | 19.3% | +3.9%p |
| 변동성 축 단독 | 110일(40%) | 8/8 | 100% | 15.5% | 19.3% | −3.9%p |
| 압축 축 단독 | 37일(14%) | 0/8 | 0% | 0.0% | 19.3% | −19.3%p |
| 모멘텀 축 단독 | 81일(30%) | 5/8 | 63% | 32.1% | 19.3% | +12.8%p |

**σ 기준** (10거래일 안에 −1.5σ 이하 · 같은 구간)

| 점수 | 포착률 | 정밀도 | 기준선 | 리프트 |
|---|---|---|---|---|
| **적응 가중** | 50% | 7.1% | 7.7% | **−0.6%p** |
| 균등 가중 | 38% | 4.6% | 7.7% | −3.1%p |
| 변동성 축 단독 | 100% | 5.5% | 7.7% | −2.2%p |

### 이 성적이 증명하는 것과 못 하는 것

**증명합니다.** 두 해 가운데 점수가 매겨진 구간의 급락 여덟 건을 **모두**, 중앙값 **5거래일
앞서** 잡았습니다. 경보가 뜬 날의 30% 가 실제 급락으로 이어졌고 아무 날이나 집었을 때는
19% 였으니, **크게 빠질 국면을 가려내는 일은 합니다**(+9.9%p). 합친 점수가 어느 단독 축보다
포착률과 리프트를 함께 갖습니다.

**증명하지 않습니다.** σ 기준으로 재면 리프트가 −0.6%p 입니다 — **「변동성이 높아졌다」는 것
이상을 알아낸다고는 아직 말하지 못합니다.** 경보 뒤 70% 는 급락으로 가지 않았으므로
**경보 하나로 매도를 권하는 근거로 삼으면 안 됩니다.** 그리고 급락 표본이 여덟 건뿐이라
포착률 100% 의 오차가 큽니다 — 한 건만 달라져도 88% 가 됩니다.

경보는 **방향을 맞히는 장치가 아니라 대비를 앞당기는 장치**입니다. 화면 맨 아래와
`notes` 의 「한계」 칸에 이 세 가지를 늘 적어 내보냅니다.

## 자료 — 어디서 오며 얼마나 믿을 수 있는가

지수 일봉을 두 해치 받아 둔 곳이 이 저장소에 없습니다. `data/market/<날짜>.json` 은 그날의
스냅숏이라 마흔 판을 다 훑어도 마흔 세션이고, 그 정도로는 볼린저(20)와 MACD(26)를 겹쳐 놓을
자리가 없습니다.

그래서 `kr100-data` 가지에 든 **시가총액 상위 종목의 2년치 일봉**을 시총 가중해 지수
하나로 묶어 코스피를 대신합니다. 주식수는 마지막 날 시총÷종가로 구해 이력 내내 고정합니다
(날마다 그날 시총으로 가중치를 다시 주면 오른 종목의 몫이 저절로 커져 지수가 실제보다 덜
떨어집니다). 코스닥 여섯 종목은 뺍니다 — 코스피를 대신할 계열에 섞을 까닭이 없습니다.

**대신하는 것이지 코스피가 아니므로, 스냅숏에 남은 실제 코스피 종가와 겹쳐 보고 그 결과를
파일에 적어 둡니다.**

| | |
|---|---|
| 구성 | 코스피 94종목, 484세션 (2024-09-19 ~ 2026-09-16) |
| 겹쳐 본 날 | 38쌍 (2026-07-23 ~ 2026-09-16) |
| **일간수익률 상관** | **0.9995** |
| 추적오차(일간) | 0.367%p |
| 연율변동성 | 프록시 76.0% / 실제 70.7% |

상관이 0.97 아래로 내려가면 `build_vol_history.py` 가 나가는 값 1 로 멈춥니다 — 대신할
자격을 잃은 것이기 때문입니다. 다만 **프록시 쪽 변동성이 실제보다 5%p 높습니다**(상위 종목에
쏠려 있기 때문). 이 도구가 내는 변동성 수치는 그만큼 높게 나오며, 화면 「지표 원본 → 이 지수는
무엇이며 얼마나 믿을 수 있는가」에 적어 둡니다.

수급·예탁금은 스냅숏에서만 나오고 52일뿐입니다. 가격 계열과 길이가 다르므로 섞어 한 계열인
척하지 않고 `flows` 로 갈라 담고, 쓰는 쪽에서 겹치는 구간만 씁니다.

## 재검산 — 실린 수를 원자료에 대고 맞춘다

```bash
python3 scripts/verify_volatility.py
```

워크플로가 판마다 돌려 `data/volatility/verify.txt` 에 남기고, **어긋난 것이 있으면 커밋을
막습니다.** 이 파일은 `vol_lib` 을 부르지 않습니다 — 같은 함수를 부르면 대조가 아니라 복사가
되므로 지표도 점수도 따로 셈해 견줍니다.

| 갈래 | 보는 것 |
|---|---|
| 가. 자료 | 봉의 날짜 차례·중복·결측, 고가≥저가, 프록시 검증값(상관·추적오차)을 다시 셈 |
| 나. 지표 | RSI·MACD·볼린저·ATR·실현변동성·이격도를 따로 셈해 대조 |
| 다. 점수 | 축이 조각들의 평균인가, 합산이 가중치대로인가, **축소 셈(λ·유효표본·사전값 혼합)이 그대로 재현되는가**, 등급이 백분위대로 붙었는가 |
| 라. **미래 참조** | **자료를 그날까지만 잘라 다시 셈해도 같은 값이 나오는가** |
| 마. 시나리오 | 확률=개수/표본인가, 합이 100인가, 리프트가 조건부−무조건부인가, 표본 하한이 지켜졌는가 |
| 바. 백테스트 | 사건 수·포착 수·정밀도·기준선을 다시 셈, 사건이 겹치지 않는가, 비교 구간이 같은가 |
| 사. 없는 것 | **값이 있는 축이 점수에서 빠지지 않았는가**, 사전값에서 온 가중치를 잰 값인 것처럼 내보내지 않았는가, 표본이 모자란데 확률이 찍혔는가, 한계를 적었는가 |

**라가 이 검산의 핵심입니다.** 백테스트 성적이 부풀려지는 가장 흔한 길은 지표가 슬그머니
미래를 보는 것인데, 그건 값을 아무리 들여다봐도 안 보입니다. 자료를 잘라서 다시 셈해 보는
것만이 잡아냅니다.

**사는 「없는 것」을 보는 묶음입니다.** 가~바는 실린 것을 대조하므로 자료가 통째로 빠지면
대조할 것이 없어 조용히 통과합니다. 실제로 처음에 「한계 문장이 있는가」를 낱말로 찾았더니,
한계 칸을 통째로 지워도 시나리오 문장에 든 「같은 국면 표본 21일」이 걸려 검사가 통과했습니다
— 지금은 갈래(`kind`)로 봅니다. 흠을 열 가지 심어 넣어 모두 잡는 것을 확인했습니다(수급 축을
점수에서 빼기, λ 를 부풀려 사전값을 잰 값인 것처럼 꾸미기, 유효표본을 중첩 무시로 적기,
음수 상관인데 잰 몫을 주기, 경고·한계 문장 지우기 등).

지금 판에서 **135짝이 맞고 어긋난 것은 없습니다.** 만드는 동안 이 검산이 실제로 잡은 것이
하나 있습니다 — 검산기 쪽이 「20일 실현변동성」을 종가 20개(수익률 19개)로 셌는데, 표준은
수익률 20개입니다. 하루 차이지만 큰 날이 하나 들고 나면서 41.4% 와 35.7% 로 갈렸습니다.

## PR 점검 (`.github/workflows/pr-check.yml`)

**이 저장소에 처음 붙는 PR CI 입니다.** 여기 있던 워크플로 열여덟은 모두 예약이거나
특정 파일이 밀렸을 때 도는 수집기라, PR 에서 도는 것이 하나도 없었습니다 — 무엇을 고쳐
올리든 사람이 눈으로 보는 것 말고는 걸러 주는 것이 없었습니다.

| 갈래 | 보는 것 |
|---|---|
| **기본** | 파이썬 대본 42개가 컴파일되는가 · 워크플로 YAML 19개가 읽히고 `jobs` 를 갖는가 · 자료 JSON 117개가 읽히는가 |
| **변동성** | 커밋된 자료가 스스로 아귀가 맞는가 → 이력·모델을 **실제로 다시 만들고** → 재검산이 통과하는가 → 그 자료로 **화면이 브라우저에서 깨지지 않는가** |

**자료가 커밋된 것과 같은지는 보지 않습니다.** 지수 일봉은 `kr100-data` 가지에 있고 날마다
자라므로 다시 만들면 커밋된 것과 당연히 달라집니다. 그래서 「같은가」가 아니라 「스스로
아귀가 맞는가」를 커밋된 판과 새로 만든 판 **둘 다**에 대고 봅니다. 프록시 상관 0.97 문턱도
여기서 함께 걸립니다.

### 왜 「커밋된 것과 같은가」를 안 보는지 — 두 가지 까닭

첫째는 위에 적은 대로 일봉이 날마다 자라기 때문입니다. 둘째는 **파이썬 판이 다르면
넷째 자리가 달라지기** 때문입니다 — 러너는 3.12, 손으로 돌리는 자리는 3.11 일 수 있고,
`statistics` 의 내부 셈이 판 사이에 바뀌어 지표에 1 ulp 가 끼고 그것이 순위상관 ρ 로
번집니다(0.2848 vs 0.2847). **모델에는 영향이 없습니다** — 가중치는 두 판 모두
57/21/18/4 로 같습니다. 그래도 바이트는 달라지므로, 같은지를 견주는 검사를 두었다면
아무 잘못 없이 빨개졌을 것입니다.

### 뜻이 같으면 파일을 건드리지 않는다

이 갱신은 하루에 예닐곱 번 돕니다(예약 둘 + 시세 파일이 밀릴 때마다). 그런데 일봉이
그대로면 모델도 그대로라, 새로 써 봐야 `generated_at_kst` 한 칸만 달라집니다. 그 한 칸
때문에 **매번 커밋이 생겼습니다** — 병합 직후 1분 사이에 같은 내용의 갱신 커밋이 둘
생기는 것을 보고 알았습니다(5fd1ceb, 4bc7881 — 차이는 시각 한 칸뿐이었습니다).

게다가 이 파일들은 **줄바꿈 없는 한 줄 JSON** 이라 git 이 줄 단위 델타를 만들지
못합니다. 한 글자가 달라도 80KB 짜리 덩이가 통째로 새로 쌓입니다.

그래서 `build_vol_history.py` 와 `build_volatility.py` 는 **시각을 뺀 내용이 같으면
파일을 그대로 둡니다.** 그러면 `generated_at_kst` 는 「이 내용이 만들어진 때」라는 제
뜻을 되찾습니다 — 「마지막으로 돌린 때」는 Actions 기록과 `verify.txt` 가 말해 줍니다.

### 화면 연기 시험 — 수가 맞아도 화면은 깨진다

```bash
python3 -m http.server 8000 &
node scripts/check_volatility_page.mjs --base http://localhost:8000 --offline <한파일판>
```

재검산은 **수**가 맞는지를 봅니다. 자료가 다 맞아도 화면은 깨집니다 — 칸 이름을 바꾸면
화면이 `undefined` 를 찍고, 차트 라이브러리를 못 찾으면 그림 자리가 통째로 빕니다. 그건
열어 봐야 드러납니다. 열아홉 가지를 봅니다 — 라이트·다크 두 판의 오류 없음, 칸 일곱,
차트 셋이 **실제로 그려졌는가**(캔버스가 있는 것과 그린 것은 다릅니다), **머리의 점수·등급·
기준일이 자료의 값과 같은가**(화면이 셈을 다시 하고 있으면 여기서 갈립니다), 네 축이 모두
서고 점수에 든 축마다 가중치가 붙었는가, 시나리오 탭이 바뀌는가, 390px 에서 가로 스크롤이
없는가, 한 파일 판이 `file://` 로 열려 그려지는가.

붙이자마자 둘을 잡았습니다.

- **한 파일 판이 `file://` 에서 될 리 없는 fetch 를 시도**해 콘솔에 오류를 남기고 있었습니다.
  자료는 심긴 것으로 잘 그려지지만, 고객에게 건네는 파일에 붉은 줄이 찍힐 까닭이 없습니다 —
  심어 둔 자료가 있고 `file://` 이면 더 받으러 가지 않게 고쳤습니다.
- **JSON 검사가 서른한 개를 걸었는데 검사 쪽이 틀린 것**이었습니다. `data/*/raw/` 는 수집기가
  파싱에 실패했을 때 무슨 응답을 받았는지 남겨 두는 진단물이라 JSON 이 아닌 것이 정상입니다
  (주소 한 줄 뒤에 404 본문이 붙거나 `<!-- 덤프: … -->` 머리글이 앞에 달립니다). 건너뜁니다.

**막아서는지 확인했습니다** — 흠을 넷 심어 모두 잡았습니다. 파이썬 오타(컴파일에서 걸림),
화면이 자료 대신 제멋대로 찍는 것(「화면 65 · 자료 57.8」로 걸림), 축 하나를 화면에서 뺀 것
(「축 넷 — 3 개만 섰습니다」), 자료 JSON 을 깨뜨린 것.

어긋나면 화면을 통째로 찍어 아티팩트로 남기므로, 러너에서 무엇이 깨졌는지 눈으로 볼 수 있습니다.

그 축이 점수에 들어간 날은 두 해 이력 가운데 34일뿐입니다. 고객에게
보여주는 자료로 쓸 경우 준법감시 부서 확인이 필요합니다.

# 매수 · 매도 타이밍 신호

`docs/signal/index.html` — **추세 · 모멘텀 · 자금수급 · 매물대** 네 축을 −100(매도) ~
+100(매수) 으로 합쳐 방향을 내고, 점수에서 멈추지 않고 **진입 · 손절 · 목표 · 비중까지
숫자로** 냅니다. 시계 넷(5 · 10 · 20 · 60거래일)을 나란히 둡니다.

대상은 **코스피 프록시 + 국내 100종목 + 미국 100종목**이고, 그 밖의 종목도 화면에서
직접 조회하면 브라우저가 그 자리에서 셈합니다.

## 먼저 읽을 것 — 이것은 수익을 늘리는 도구가 아닙니다

백테스트가 말하는 것을 요약부터 적습니다. 화면 맨 아래 작은 글씨로 미루지 않습니다.

| 물음 | 답 |
|------|-----|
| 매수후보유보다 많이 버는가 | **아니오.** 국내 기준 −22 ~ −30%p, 이긴 종목은 20~23% 뿐 |
| 왜 지는가 | 두 해가 오르는 장이었고 이 규칙은 **장에 18~30% 만 머뭅니다** |
| 그럼 무엇을 하는가 | **최대낙폭을 절반 가까이 줄입니다** — 국내 −23~−28% 대 보유 −46% |
| 진입이 아무 날이나 사는 것보다 나은가 | 국내는 **네 시계 모두 앞섭니다**(20일 건당 +3.87% 대 −3.98%) |
| 흔한 규칙(20일선 돌파)보다 나은가 | 예 — 그쪽은 −15 ~ −29%p 로 더 집니다 |
| 통계적으로 증명됐는가 | **아니오.** 아래 「열여섯 번 시험했다」 참고 |

**겪는 낙폭을 줄이는 도구로 읽으십시오.** 「이 신호를 따르면 더 법니다」는 이 자료가
받쳐 주지 않는 말입니다.

## 미국 종목은 신호가 거꾸로 갑니다

| 시장 | 5일 | 10일 | 20일 | 60일 | 읽기 |
|------|-----|------|------|------|------|
| 국내 | +1.00 | +1.09 | +0.95 | +1.26 | 넷 다 양수 — 방향은 일관 |
| 미국 | −0.07 | −0.09 | −0.43 | **−2.02** | **넷 다 음수 — 따르지 마십시오** |

(신호일 이후 h일 수익률 − 같은 종목 같은 구간 평상시, %p)

미국 100종목에서는 신호가 높던 날 뒤가 **오히려 평상시보다 나빴고**, 60일 시계는 낱개로
보면 유의하기까지 합니다(95% 구간 −3.41 ~ −0.59). 이 사실은 화면에서 미국 종목을 열면
**종목 바로 옆에 붉은 상자로** 뜹니다 — 한계 문단에만 적으면 「적극 매수」만 보고 창을
닫는 사람에게는 닿지 않기 때문입니다.

왜 갈리는지는 이 자료로 답하지 못합니다. 국내 수급 구조(외국인·기관 쏠림) 때문일 수도
있고, 두 해 미국 장이 지수 주도로 올라 개별 종목의 되돌림 신호가 통째로 틀렸을 수도
있습니다. **모르는 것을 모른다고 적어 둡니다.**

## 열여섯 번 시험했습니다

시계 4 × 부호전환 2 × 시장 2 = **16 가지**를 쟀습니다. 5% 수준으로 보면 **전부 우연이어도
한 가지쯤은 유의하게 나옵니다.** 그 하나를 집어 싣는 것이 백테스트가 거짓말하는 가장
흔한 방식입니다.

- 낱개로 유의: 국내 5일 +1.00%p (p=0.021), 미국 60일 −2.02%p (p=0.005)
- Bonferroni 보정 문턱: p < 0.0031
- **보정을 통과한 조합: 없음**

남는 것은 **국내가 네 시계 모두 양수라는 방향의 일관성**뿐이고, 그건 증거지 증명이
아닙니다.

신뢰구간은 종목이 아니라 **날짜 블록**으로 뽑았습니다. 200종목 × 484세션 = 96,800
종목일이라 표본이 커 보이지만, 같은 날 한국 주식 백 개는 거의 같이 움직여 **독립 관측은
날짜 수에 가깝습니다.** 종목일을 독립으로 세면 구간이 √100 배 좁아져, 우연히 생긴 차이가
유의해 보입니다.

## 네 축

고정 문턱(「RSI 30 이하면 과매도」)을 쓰지 않습니다. 지표마다 **제 과거 1년 안에서의
백분위**로 옮겨, 변동성이 연 15% 인 종목과 70% 인 종목에서 같은 뜻이 되게 합니다.

| 축 | 보는 것 | 쓰는 지표 |
|----|---------|-----------|
| **추세** | 어느 쪽으로 가고 있는가 | MA 배열, MACD 히스토그램, 20일선 기울기, 60일 이격도, ADX·DI, 지수 대비 상대강도 |
| **모멘텀** | 얼마나 밀렸는가 — **부호가 국면에 따라 뒤집힙니다** | RSI, 스토캐스틱, 볼린저 %b, 5·20일 수익률 |
| **자금수급** | 돈이 들어오는가 | OBV 기울기, MFI, 거래량 z (오른 날 터졌는지 내린 날 터졌는지로 부호를 붙임) |
| **매물대** | 머리 위에 물량이 얼마나 걸려 있는가 | 현재가 위/아래 거래대금 비중, POC 거리, 가치영역 돌파 |

**압축(볼린저·켈트너 스퀴즈)은 방향 점수에 넣지 않습니다.** 눌린 것은 「곧 크게 움직인다」
이지 「어디로」가 아니기 때문입니다. 대신 **확신도**에 곱해 비중을 정하는 데 씁니다.

### 모멘텀의 부호를 뒤집는 장치

RSI 70 은 추세장에서 「더 간다」이고 횡보장에서 「되돌린다」입니다. 대부분의 도구가 이걸
하나로 고정해 두고 **둘 중 한 장세에서 반드시 틀립니다.** 여기서는 ADX 로 국면을 재서
(20 이하 횡보 ~ 30 이상 추세) 부호를 섞습니다.

값을 하는지 따로 쟀습니다 — 켠 판과 끈 판을 나란히 돌립니다.

| | 5일 | 10일 | 20일 | 60일 |
|---|---|---|---|---|
| 국내, 부호전환 **켬** | +1.00 | +1.09 | +0.95 | +1.26 |
| 국내, 부호전환 **끔** | +0.64 | +0.95 | +0.61 | +1.33 |

국내 세 시계에서 보탬이 됐고 60일에서는 오히려 나빴습니다. 미국에서는 대체로 나빴습니다.
**부분적으로만 맞았다**는 뜻이라 켠 판을 기본으로 두되 이 표를 함께 싣습니다.

### 가중치는 자료가 정하되, 표준오차를 못 넘으면 0 으로 둡니다

축마다 「그 점수가 높던 날 뒤가 실제로 좋았는가」의 순위상관을 **그 시점 이전 자료로만**
재고(워크포워드), 증거의 힘 λ 만큼 사전값(균등 25%)과 섞습니다.

여기에 한 겹을 더 두었습니다. 처음에는 **ρ=0.05 인 축이 ρ=0 인 축들을 92% 대 2.5% 로
눌렀습니다.** 양수 몫의 비율로 나누기 때문에, 하나만 간신히 양수면 그것이 다 가져갑니다.
그런데 유효관측 87개에서 순위상관의 표준오차는 0.11 이라 **ρ=0.05 는 0 과 구별되지 않는
값**입니다. 구별되지 않는 것에 92% 를 주는 것은 잡음을 실력으로 읽는 일입니다.

그래서 |ρ| 에서 **표준오차 하나를 빼고 남는 만큼만** 씁니다. 못 넘는 축은 0 이 되어
사전값 쪽에 남고, 넷이 다 0 이면 균등가중 그대로 갑니다.

음수 상관은 **뒤집지 않습니다.** 두 해 자료에 맞춘 것이 되기 쉽기 때문입니다. 잰 값은
산출물에 그대로 적어 두어, 뒤집어야 할 만큼 꾸준히 음수라면 자료가 쌓이며 드러나게 합니다.

## 점수는 타이밍이 아닙니다

「82점」은 언제 사서 어디서 손절할지를 말해 주지 않습니다. 그래서 숫자까지 냅니다.

- **진입** — 신호 자기백분위가 70 위로 **올라선 날**. 높은 날을 모두 세면 한 번 오른 뒤
  여러 날 높게 머무는 구간이 진입 여러 건으로 부풀어 성적이 왜곡됩니다. 타이밍은
  「높다」가 아니라 「높아졌다」입니다.
- **손절** — `진입가 − 2×ATR14` 와 매물대 지지 가운데 **가까운 쪽**. 매수 신호에는 손절이
  반드시 붙고, 검산기가 그걸 확인합니다 — 손절 없는 매수 신호는 신호가 아니라 감상입니다.
- **목표** — 머리 위 매물대. 없으면 손절폭의 1.5배.
- **비중** — 연 20% 를 목표 변동성으로 두고 그 종목의 실현변동성과 확신도로 줄입니다.
  연 60% 짜리와 15% 짜리를 같은 금액으로 들면 앞엣것이 손익을 통째로 좌우합니다.

백테스트의 진입은 **신호 다음 날 시가**입니다. 당일 종가에 사는 것으로 하면 종가를 보고
그 종가에 사는 것이 되어 성적이 부풀어 오릅니다. 갭하락으로 손절가 아래에서 열리면
**시가로 체결**합니다.

이 시계에서는 비용으로 결론이 뒤집히지 않습니다. 다만 보유기간을 더 줄이면 뒤집힙니다.

## 시나리오 확률

오늘과 **같은 신호대**였던 과거 날들의 이후 분포를 냅니다. **표본 20일 미만이면 확률을
내지 않고 모자라다고 적습니다** — 아무 말도 못 하는 것이 틀린 말을 하는 것보다 낫습니다.

점수와 확률이 어긋나는 일이 있습니다(「적극 매수」인데 같은 신호대였던 과거의 25% 만
올랐다). **그걸 감추지 않고 화면에 노란 상자로 적습니다.** 둘이 다를 때는 표본 수를 함께
보고 판단하십시오 — 점수는 지표의 지금 자리이고, 확률은 그 자리였던 과거의 결과입니다.

## 종목별 외국인 · 기관 수급 — 오늘부터 쌓습니다

`scripts/fetch_stock_flows.py` 가 날마다 모아 `data/flows/kr100.json` 에 **쌓습니다**
(`.github/workflows/stock-flows.yml`, 평일 19:00 · 20:30 · 22:00 KST). 지금까지는
`index.html` 이 브라우저에서 네이버를 직접 부르는 구조라 서버에 쌓인 것이 없었습니다.

**왜 저녁 세 번인가 — 재어 보고 정했습니다.** 처음에는 장 마감 뒤 17:00 / 18:00 으로
잡았는데, 그 예약이 한 번도 도는 것을 못 보고 손으로 두 번 돌려 보니 네이버가 그
시각에는 아직 그날치를 안 올려 두고 있었습니다.

| 수집 시각 | 받은 마지막 날짜 |
|---|---|
| 16:14 KST | 전날까지 — **그날치 없음** |
| 21:28 KST | 그날까지 |

수집기는 날짜로 병합하므로 여러 번 돌아도 덧나지 않고, 앞에서 못 받았으면 뒤에서
받습니다. 이 저장소에서 예약이 5시간씩 밀리는 것을 여러 번 보았기 때문에 세 번으로
벌려 둔 것은 그 대비이기도 합니다.

**그날치가 빠졌으면 말합니다.** 병합 구조라 네이버가 안 올렸으면 어제 것을 그대로
다시 쓰고 조용히 성공합니다 — 실제로 그래서 하루 늦은 수급으로 신호를 낸 적이
있습니다. `verify_stock_flows.py` 의 `verify_freshness` 가 수급의 마지막 날짜를
**일봉의 마지막 거래일**과 맞대어 뒤졌으면 `[STALE]` 로 적고, 워크플로가 그 자국을
읽어 경고를 띄웁니다. 실패가 아니라 경고인 까닭은, 네이버가 늦는 것은 고칠 수 있는
일이 아니고 받아 둔 날들은 늦었어도 버릴 것이 아니기 때문입니다 — 막아야 할 것은
**낡았다는 사실이 보이지 않는 것**이지 낡은 자료 자체가 아닙니다.

**뒤로 못 갑니다.** 네이버가 종목별 수급을 길게 내주지 않으므로 오늘부터 모으는 수밖에
없고, 하루를 거르면 그날은 영영 빕니다. 그래서 예약을 두 번 걸고 실패하면 시끄럽게
끝냅니다.

쌓이는 만큼 자금수급 축에 저절로 들어갑니다. 넘어야 할 문턱은 없습니다 — **증거의 힘
λ** 가 자료량에 따라 올라가며 가중치를 옮겨 줍니다. 없는 날은 **없는 채로** 둡니다.
0 으로 채우면 「사지도 팔지도 않았다」가 되어 자료가 빠진 날마다 축이 중립으로 끌려갑니다.
20일 누적은 창 안에 빠진 날이 절반을 넘으면 내지 않습니다 — 두 날치로 잰 「20일 누적」은
20일 누적이 아닙니다.

**지금은 아직 점수에 들어가지 않습니다.** 열 세션뿐이라 20일 누적이 서지 않고 z점수의
최소관측(15)도 못 채웁니다. 스무 세션쯤 쌓이면 들어가기 시작합니다. 화면은 이 두 상태를
**갈라 적습니다** — 들어가기 전에는 「아직 점수에 들어가지 않습니다」, 들어간 뒤에는
「N 일이 점수에 들어갔고 **백테스트는 이 자료 없이 잰 것**입니다」. 「N 세션 실렸습니다」만
적으면 급히 보는 사람은 반영된 줄로 읽습니다. `verify_signals.py` 와
`check_signal_page.mjs` 가 상태에 맞는 문구가 실제로 뜨는지 봅니다.

### 이 수집기는 만든 자리에서 돌려 보지 못했습니다

만든 세션은 `finance.naver.com` · `m.stock.naver.com` 으로 나가는 길이 막혀 있었습니다
(에이전트 프록시가 CONNECT 에 403). **살아 있는 응답에 대고 맞춰 본 적이 없고**, 필드
이름은 `index.html` 이 쓰고 있는 것을 그대로 가져왔을 뿐입니다.

그런 처지에서 할 수 있는 것은 **파서가 틀렸을 때 조용히 지나가지 않게** 하는 것입니다.

| 검증 | 무엇을 잡는가 |
|------|---------------|
| 빈 판 거르기 | 하나도 못 받았거나 죄다 0 이면 **실패로 끝내고 커밋하지 않습니다** |
| 종가 대조 | 거래일 집합이 `kr100-data` 일봉과 정확히 겹치는가 (값 차이는 느슨한 문턱) |
| 날짜 밀림 | lag −1 · 0 · +1 로 맞춰 보고 **lag 0 이 가장 잘 맞아야** 합니다 |
| **시장 합 대조** | KR100 외국인 순매수의 합이 이미 갖고 있는 **시장 전체 수급**과 같이 움직이는지 |

마지막이 제일 셉니다 — **제 파싱 가정에 기대지 않고 다른 출처와 맞대 보는 유일한
자리**입니다. 부호를 뒤집어 읽었으면 상관이 음수로, 주식수를 금액으로 착각했으면 종목마다
주가가 달라 합이 엉켜, 칸이 밀려 거래량을 읽었으면 언제나 양수가 되어 무너집니다.

`scripts/check_stock_flows.py` 가 **네트워크 없이** 이 검증기들이 실제로 흠을 잡는지
확인합니다(시험 34 가지). 부호 뒤집기 · 단위 백 배 · 칸 밀림 · 0 메우기 · **날짜 밀림** ·
종가 어긋남 · 길이 어긋남 · 보유율 범위 · 단위 누락 **열 가지를 심어 모두 잡는 것을
보았습니다.** 여기에 **낡은 판**(그날치가 빠진 판·수급이 일봉보다 앞서는 판)을 따로
시험합니다 — 그건 실패가 아니라 경고라서 흠 심기 틀(실패만 봅니다)로는 안 잡히기
때문입니다. 잣대가 되는 「일봉의 마지막 거래일」은 **고정해서 넣습니다**. 저장소의 진짜
일봉을 쓰면 코드가 그대로인데 어제는 통과하고 오늘은 실패하는 시험이 됩니다.
파서가 맞는지는 아직 모르지만, **틀렸을 때 잡히기는 하는가**는 증명해 두었습니다 —
그래야 통과가 찍혔을 때 그게 「맞다」인지 「검산기가 눈을 감았다」인지 가릴 수 있습니다.

GitHub Actions 에서 실제로 돌렸습니다(100종목 전부, 네 번). **파서가 맞는 것을 세
방향에서 확인했습니다.**

아니라 두 출처가 종가를 다르게 보고 있었습니다.**

- 거래일은 완벽히 정렬 — 날짜 밀림이 아님
- 어긋남이 양쪽으로 거의 반반(수급이 높은 건 16 / 낮은 건 23), 크기는 중앙 0.96% ·

- `278470.KS 2026-09-14` 수급 363,500 이 **일봉 저가 365,000 보다 낮음** — 같은 세션

그래서 그 검사는 잡으려던 것(날짜 밀림·칸 밀림)이 아니라 **「두 벤더가 같은 종가를
쓰는가」를 재고 있었습니다.** 느슨하게 고친 것이 아니라 의도한 것을 재도록 갈랐습니다 —
거래일 정렬과 lag 시험으로 날짜 밀림을 직접 묻고, 칸 밀림은 시장 합 대조가 이미
배제하며, 벤더 불일치는 **실패가 아니라 경고**로 남깁니다.

**이건 알아 둘 일입니다.** 이 도구의 지표(RSI·MACD·볼린저·ATR·매물대…)는 **모두 일봉
(Yahoo)으로 셈합니다.** 종목일의 15.6% 에서 두 출처의 종가가 중앙 0.96% 어긋나는데,
어느 쪽이 맞는지는 이 자료로 가릴 수 없습니다. **일봉 쪽이 틀린 만큼은 지표에도
들어갑니다.** 표본이 열흘뿐이라 이 비율 자체의 오차도 큽니다.

## 엔진이 두 벌인 까닭과, 그것을 맞추는 장치

미리 셈해 둔 종목(지수 · KR100 · US100)은 서버가 셈해 `data/signals/latest.json` 에 담고
**화면은 옮겨 찍기만 합니다.** 화면이 다시 셈하면 검산 대본이 대조할 자리가 없어집니다.

그런데 **임의 종목은 서버에 자료가 없어** 브라우저가 받아서 그 자리에서 셈해야 합니다.
그래서 `scripts/signal_lib.py` 와 `docs/signal/signal_engine.js` 두 벌이 됩니다. 갈라지면
화면과 백테스트가 서로 다른 신호를 내는데, 그건 둘 중 하나가 틀린 것보다 나쁩니다 —
어느 쪽이 맞는지 알 수 없기 때문입니다.

`make_signal_golden.py` 가 파이썬 기준값을 박아 두고 `check_signal_golden.mjs` 가
대조합니다(**1,240 가지, 어긋남 없음**). 그 대조가 실제로 흠 둘을 잡았습니다.

- 파이썬이 **표시용으로 세 자리 반올림한 λ 를 도로 읽어 셈에 쓰고** 있었습니다
  (`vol_lib.fit_weights` 에서 물려받은 것). 가중치가 1e−4 쯤 달라질 뿐이라 아무 데서도
  터지지 않는 종류의 흠입니다.
- `composite` 의 반올림 자리가 두 쪽에서 달랐습니다.

볼린저밴드는 **표본표준편차(ddof=1)** 로 세웁니다. 교과서는 모표준편차(÷n)를 쓰지만
이 저장소가 `vol_lib.rolling_std` 에서 ÷(n−1) 로 두었고 변동성 경보 모델이 그걸 따릅니다.
밴드가 2.6% 넓습니다. 교과서 쪽으로 되돌리면 **두 모델이 서로 다른 밴드를 쓰게 되어**
화면 위아래가 어긋나므로, 저장소 약속에 맞추고 이렇게 적어 둡니다.

## 검산

`scripts/verify_signals.py` — 실린 수를 **원자료에서 따로 셈해** 대조합니다(**11,461 가지**).
같은 함수를 불러 같은 값이 나오는 것을 확인하는 시험은 아무것도 검산하지 않습니다.

| 미래참조 | 자료를 그날까지 **잘라** 다시 셈해 같은 값이 나오는가 (지표 · 축 · 워크포워드 가중치) |

마지막 줄이 없으면 나머지는 통과했다는 말을 할 자격이 없습니다. 안 잡히는 검산기는
통과만 찍는 장식입니다.

**만드는 동안 실제로 흠을 잡았습니다.** 매물대를 닷새마다만 다시 세면서 **현재가 위아래
비중까지 낡은 종가로 재고** 있었습니다 — 값이 조금 틀리는 정도가 아니라 **지지선이
현재가 위에 찍히는** 일까지 났습니다. 「아래 비중이 있을 수 있는 범위를 벗어난다」가
그걸 잡았습니다. 물량표를 세는 것과 오늘 종가로 읽는 것을 나누어 고쳤습니다.

`scripts/check_signal_page.mjs` 가 헤드리스 브라우저에서 화면을 봅니다(24 가지) —
라이트/다크 둘 다, 자바스크립트 오류, 손절 없는 매수 칸이 있는지, **미국 종목에 경고가
뜨는지**, 폰 너비에서 가로로 밀리지 않는지.

### 인터넷 없는 PC 용 한 파일 판

인터넷이 막힌 업무용 PC 에서는 화면이 어떤 경로로도 자료를 못 받습니다. 파일 옆에
json 을 같이 두는 것도 안 됩니다 — 브라우저가 `file://` 로 열린 페이지의 옆 파일
읽기를 CORS 로 막기 때문입니다(origin `null`). 그래서 자료를 HTML 안에 심습니다.
`kr-top100-offline.html` 과 같은 방식입니다.

`scripts/make_signal_offline.py` 가 `latest.json`(201종목) · `backtest.json` ·
`signal_engine.js` 를 `docs/signal/index.html` 안에 접어 넣어 **4.4MB 파일 하나**를
만듭니다.

**화면 코드를 두 벌로 만들지 않았습니다.** 갈림은 `index.html` 의 `loadJson()` 하나뿐이고
— 내장 블록이 있으면 그것을, 없으면 `fetch` 를 씁니다 — 그리는 코드는 인터넷판과
같은 것입니다. 내장판용으로 화면을 베껴 두면 두 벌이 되어 언젠가 조용히 어긋납니다.

되는 것과 안 되는 것을 갈라 둡니다.

| | |
|---|---|
| 된다 | 지수 · KR100 · US100 201종목의 네 시계 신호 · 축 · 매물대 · 시나리오 · 차트. **인터넷 0바이트** |
| 안 된다 | 임의 종목 조회 — 일봉을 새로 받아야 하는 일입니다. 화면이 **그 까닭을 그대로 적습니다**(종목코드가 틀렸다고 적으면 멀쩡한 코드를 몇 번씩 다시 치게 됩니다) |

`scripts/check_signal_offline.mjs` 가 **바깥으로 나가는 요청을 전부 끊고** `file://` 로
열어 봅니다(34 가지). 나간 요청이 한 건이라도 있으면 실패입니다 — 그래야 「내 PC 에서는
되던데」가 아니라 정말로 자급자족하는지 알 수 있습니다. 라이트/다크 둘 다에서 201종목
목록 · 차트 · 매물대가 그려지는지, 손절 없는 매수 칸이 없는지, 미국 종목 경고가 뜨는지,
머리말이 **내장 스냅샷임을 밝히는지**(오래된 파일을 실시간으로 착각하면 안 됩니다),
임의 종목 실패 사유가 바른지를 봅니다.

이 검산기도 흠을 심어 확인했습니다 — 내장 자료 블록을 지운 판과 엔진을 바깥 파일로
되돌린 판, 둘 다 걸렸습니다.

## 돌리는 법

```bash
# 1) 신호 셈하기 — kr100-data · us100-data 가지가 필요합니다
python3 scripts/build_signals.py --market KR,US

# 2) 재검산 — 어긋나면 나가는 값이 1
python3 scripts/verify_signals.py

# 3) 파이썬 ↔ JS 엔진 대조
node scripts/check_signal_golden.mjs

# 4) 화면 — 로컬 서버로 엽니다
python3 -m http.server 8000
#   http://localhost:8000/docs/signal/

# 5) 화면 점검 (헤드리스)
node scripts/check_signal_page.mjs

# 6) 인터넷 없는 PC 용 한 파일 판 — 자료를 HTML 안에 심습니다 (4.4MB)
python3 scripts/make_signal_offline.py      # → signal-offline.html
node scripts/check_signal_offline.mjs       # 바깥 요청을 전부 끊고 file:// 로 열어 봅니다

# 7) 종목별 수급 — 네트워크가 되는 곳에서만 (자체 시험은 어디서나 됩니다)
python3 scripts/check_stock_flows.py        # 네트워크 없이 — 검산기가 흠을 잡는지
python3 scripts/fetch_stock_flows.py        # 모으기
python3 scripts/verify_stock_flows.py       # 종가·시장합 대조

# 8) 백테스트 — 10분쯤 걸립니다. 모델을 고쳤을 때만 돌립니다.
python3 scripts/signal_backtest.py --market KR,US --h 5,10,20,60 \
  --out data/signals/backtest.json
```

자동화는 `.github/workflows/stock-flows.yml`(평일 19:00 · 20:30 · 22:00 KST) →
`signals.yml` 차례로 돌고, `signals-backtest.yml` 은 손으로만 돌립니다.

**둘을 잇는 것은 `workflow_run` 입니다.** `signals.yml` 의 push 방아쇠에
`data/flows/kr100.json` 이 적혀 있지만 그것만으로는 연결이 되지 않습니다 —
**GITHUB_TOKEN 이 만든 커밋은 다른 워크플로를 부르지 않습니다**(재귀 실행을 막으려는
깃허브 규칙이고, `fund-weekly.yml` 주석에도 같은 말이 있습니다). 그래서 수급
워크플로가 커밋해도 신호는 안 돌고 다음 날 예약까지 기다렸습니다. `workflow_run` 은
앞 워크플로가 **끝났다는 사실**에 걸리는 것이라 그 규칙에 걸리지 않습니다. 앞이
실패했을 때도 발동하므로 `conclusion == 'success'` 일 때만 잇습니다 — 수급 수집이
넘어졌는데 신호를 새로 내면 낡은 수급으로 셈한 판을 「방금 갱신함」으로 덮어씁니다.

`signals.yml` 의 예약(17:40 · 18:30 KST)은 수급보다 앞서므로 그날 수급을 못 봅니다.
그 판은 전날 수급으로 나가고, 저녁에 수급이 들어오면 위 연결이 다시 돌려 그날 것으로
갈아 끼웁니다. **백테스트를 예약으로 돌리지 않는 까닭** — 성적이
날마다 조용히 바뀌면 어제 「−22%p」를 보고 판단한 사람과 오늘 「−19%p」를 보는 사람이
서로 다른 자료를 쓰게 됩니다.

## 유의사항 (매수 · 매도 타이밍 신호)

정보 제공 목적의 사내 참고 자료이며 **투자 권유가 아닙니다.** 신호는 과거 자료로 만든
규칙의 출력이지 앞일에 대한 예측이 아닙니다.

**매수후보유보다 더 버는 것을 보이지 못했습니다** — 국내 기준 시계 어디서도 앞서지
못했고(−22~−30%p), 이긴 종목은 20~23% 뿐입니다. **미국 종목은 시계 넷이 모두 음수라
신호를 그대로 따라서는 안 됩니다.** 열여섯 가지 조합을 시험했고 **여러 번 시험한 것을
보정하면 유의한 조합이 하나도 없습니다.**

백테스트 구간은 두 해뿐이고 그 두 해는 **오르는 장 한 국면**입니다(국내 100종목 중앙값
+31.8%). 하락장에서 어떻게 되는지는 이 자료가 답하지 못합니다. 종목별 외국인·기관 수급은
아직 반영되지 않았습니다. 지수는 실제 코스피가 아니라 시총 상위 종목으로 세운
**프록시**입니다. 임의 종목 조회는 브라우저가 셈한 값이라 **검산도 백테스트도 거치지
않았습니다.**

고객에게 보여주는 자료로 쓸 경우 준법감시 부서 확인이 필요합니다.
