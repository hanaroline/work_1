# 금융자료 데이터 정합성 (fin-data-integrity)

## 이 스킬이 존재하는 이유

금융자료의 오류는 "몰라서" 나지 않습니다. **확인되지 않은 것을 매끄러운 문장으로 덮으려는 압력**에서 납니다.
빈칸이 있는 표는 미완성처럼 보이고, "미확인"이라는 단어는 자료의 완성도를 깎아먹는 것처럼 느껴집니다.
그래서 "찾지 못했다"가 "존재하지 않는다"로, "8월 18일 기사"가 "8월 18일 발표"로, "기사에 나온 누군가의 발언"이 "그 기관의 공식 전망"으로 조용히 승격됩니다.

이 승격은 리서치 단계에서 일어나지 않습니다. **리서치 노트를 산출물로 옮겨 적는 순간** 일어납니다.
그래서 이 스킬의 핵심은 더 열심히 검색하는 게 아니라, **노트와 산출물 사이에 기계가 읽는 중간 단계를 하나 끼워넣는 것**입니다.

완벽한 금융자료는 모든 칸이 채워진 자료가 아닙니다. **확인된 것과 확인되지 않은 것이 독자에게 구분되어 보이는 자료**입니다.

## 작업 순서

빌드가 검증보다 **먼저** 오면 안 됩니다. 순서 자체가 이 스킬의 내용입니다.

```
1. 리서치        → 수치·전망·발언 수집 (출처 URL 필수 동반)
2. 주장 대장 작성 → 인쇄될 모든 수치를 claims.json 에 등록
3. 기계 검산      → python scripts/check_claims.py claims.json
4. 검산 통과 후 빌드 → PPT/Word/HTML 제작 (대장에 없는 수치는 쓰지 않음)
5. 인도 전 게이트  → 아래 '인도 전 게이트' 확인
```

3번이 실패하면 4번으로 가지 않습니다. 대장을 고치거나, 해당 수치를 자료에서 뺍니다.

## 2단계: 주장 대장 (claim ledger)

`scripts/ledger_template.json` 을 복사해서 시작합니다. **산출물에 인쇄될 모든 숫자**는 대장에 한 줄을 갖습니다. 대장에 없는 숫자를 슬라이드에 쓰지 않는 것이 이 절차의 전부입니다.

각 주장에 필요한 필드:

| 필드 | 왜 필요한가 |
|---|---|
| `value` + `unit` | 단위 없는 숫자는 나중에 반드시 잘못 해석됩니다. `USD/BRL 4.50` 을 `4.50원`으로 쓰는 사고가 여기서 막힙니다 |
| `series` | 같은 통화쌍도 피드마다 다릅니다(장중/종가/뉴욕정오). 한 산출물 안에서 한 쌍은 한 계열로 통일 |
| `as_of` | "현재"라는 말은 자료가 남는 순간 거짓이 됩니다 |
| `tier` | 1차/2차/3차 (→ `references/source-tiers.md`) |
| `source_url` | 없으면 그 수치는 쓸 수 없습니다 |
| `announced_on` | **보도일과 다릅니다.** 기관 전망치의 경우 원 보고서 발표일 |
| `attributed_to` | 발언·전망의 실제 주체(기관 + 사람). 한 기사에 여러 전문가가 나오는 경우가 흔합니다 |
| `verdict` | `confirmed` / `unverified` / `refuted` |
| `render` | `unverified` 일 때 자료에 어떻게 표시할지: `omit` 또는 `marked` |

`verdict: unverified` 인 항목에 `render: assert` 는 스크립트가 거부합니다. 이게 이 스킬의 가장 중요한 한 줄입니다.

파생 수치(변동률·교차환율·시나리오·요인분해)는 `derived` 배열에 넣습니다. 직접 계산하지 말고 스크립트가 계산한 값을 쓰십시오.

## 3단계: 기계 검산

```bash
python scripts/check_claims.py claims.json          # 검사
python scripts/check_claims.py claims.json --fix    # 파생값을 계산값으로 덮어쓰기
```

스크립트가 잡는 것 — **전부 추가 검색이 필요 없는 항목들이고, 실제 사고의 절반이 여기서 납니다**:

- 인쇄된 변동률이 실제 계산과 다름
- 교차환율 불일치 (A/B × B/C ≠ A/C)
- 같은 통화쌍에 두 개의 계열이 섞임
- 요인분해 기여도 합이 100%가 아님
- 시나리오 산술 오류
- `unit` 누락 또는 같은 지표에 단위 혼용
- `source_url`·`as_of`·`tier` 누락
- `verdict: refuted` 인데 자료에 남아 있음
- `unverified` + `render: assert`
- tier 3(위키·블로그·집계사이트) 단독 근거

## 4단계: 빌드 규칙

**부정 단정을 만들지 않습니다.** "X 기관은 전망치를 공표하지 않는다"는 검색 실패로는 쓸 수 없는 문장입니다. 쓸 수 있는 문장은 "공개 자료에서 확인되지 않음(2026.8.27 기준)"입니다. 어떤 기관이 무엇을 안 한다는 주장은 그 기관의 발간 목록을 직접 확인했을 때만 씁니다.

**기관 전망치는 4가지를 한 셀에 함께 적습니다**: 기관 · 발표일 · 대상시점 · 조정방향.
조정방향(상향/하향)을 빠뜨리거나 뒤집으면 전망의 의미가 반대로 전달됩니다. 하향 조정을 "상향"으로 쓰면 그 기관이 정반대를 말한 것이 됩니다.

**발언은 원문에서 화자를 확인한 뒤 인용합니다.** 언론 기사 한 건에 은행 연구원·교수·당국자가 함께 등장하는 것이 표준입니다. 요약본만 보고 발언을 붙이면 귀속이 섞입니다.

**계열은 산출물 단위로 통일합니다.** `series_policy` 에 통화쌍별 채택 계열을 선언하고, 다른 계열의 값은 각주로만 병기합니다.

**미확인 항목은 시각적으로 구분합니다.** 회색 처리, `n/a`, 별도 각주 중 하나를 쓰고, 그럴듯한 문장으로 채우지 않습니다.

## 5단계: 인도 전 게이트

산출물을 보내기 전에 확인합니다. 보낸 뒤에 하는 검증은 이미 늦습니다.

- [ ] `check_claims.py` 통과 (경고까지 읽었는가)
- [ ] 산출물의 모든 숫자가 대장에 있는가 (역방향 확인 — 슬라이드에서 대장으로)
- [ ] 기관 전망 셀에 발표일·대상시점·조정방향이 있는가
- [ ] 발언 인용의 화자를 원문에서 확인했는가
- [ ] 부정 단정("~하지 않는다", "~없다")이 실제 확인에 근거하는가
- [ ] 미확인 항목이 단정문으로 섞여 있지 않은가
- [ ] 각주에 계열 정책과 기준일이 적혀 있는가
- [ ] 시각 검증 완료 (PPT/HTML은 렌더링해서 직접 볼 것)

## 사용자에게 보고할 때

**확인된 것과 확인되지 않은 것을 나눠서 보고합니다.** 미확인 항목을 언급하지 않고 넘어가는 것은 그 항목을 확인된 것처럼 전달하는 것과 같습니다.

보고에 포함할 것: 재검증 기준일 / 1차 출처로 확인한 항목 / 2차 출처만 있는 항목 / 확인 실패한 항목과 그 이유(유료·robots 차단 등) / 사용자가 직접 확인해야 할 지점.

접근 차단으로 확인이 안 된 항목은 숨기지 말고, 어디서 확인할 수 있는지 알려줍니다. 예: "BCB Focus는 공식 PDF 접근 실패로 언론 2곳 교차확인. 정식 인용 시 bcb.gov.br의 해당 주차판 직접 확인 권장."
